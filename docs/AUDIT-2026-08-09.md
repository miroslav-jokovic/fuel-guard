# FuelGuard — Engineering Audit & AI-Codegen Failure Analysis

**Date:** 9 August 2026
**Scope:** the full monorepo (6 apps, 7 packages, 158 migrations, ~106k LOC non-test source, ~25k LOC tests, 2,124 unit test cases, 311 matrix assertions)
**Method:** seven parallel deep-audit passes (security, database/RLS, business logic, test integrity, architecture, docs-vs-reality, frontend), then two adversarial verification passes that re-checked every high-severity claim against the code. Findings that failed verification were downgraded or dropped. Where a claim depends on runtime configuration I cannot see, it is marked **VERIFY** with the exact query or setting to check.

---

## 1. The honest headline

**This is a well-built codebase.** That is not a courtesy — it is the audit result, and it matters because it changes what you should do next. Specifically, and unusually for a platform built largely with AI assistants:

- **All 83 live tables have RLS enabled.** There is exactly one `USING (true)` in 158 migrations and it is correctly scoped to `supabase_auth_admin`. All 47 `SECURITY DEFINER` functions pin `search_path`.
- **No money is stored as float.** Every monetary column is `numeric(p,s)`. Every timestamp is `timestamptz`. Neither is common.
- **Zero cross-app imports, zero package→app imports, zero runtime import cycles.** The layering actually holds.
- **The unit suite is real.** Across 2,124 test cases I found *one* tautological assertion, zero `it.only`, zero snapshot-only tests, zero swallowed failures.
- **The team already built four custom CI fitness functions** (file size, function size, feature boundaries, design-token parity) — the exact control class the industry literature recommends as the antidote to AI-driven architectural drift.
- **The migration headers and code comments are the best documentation in the repo**, and several are honest post-incident write-ups (`0123_identity_uniqueness.sql`, `0135_driver_fuel_write_closure.sql`).

So the problem is not that the code is bad. The problem is a specific, recognisable pattern, and it has three shapes that repeat everywhere:

> **1. A helper gets built and adoption stops at ~20%.** `lib/paging.ts` has 5 adopters and 25 hand-rolled copies still live. `lib/format.ts` has 5 importers and 8 competing local implementations. The abstraction exists, its doc comment claims the consolidation *happened*, and the divergent copies keep accumulating behind that claim.
>
> **2. Hardening travels in one direction only.** The driver's `apiFetch` learned timeouts, `Retry-After` handling and Zod validation. The web's never did. The API's EFS reader learned magic-byte validation and an RFC-4180 tokenizer. The web's never did. Each fix was real; none was back-ported; no test pins the pair together.
>
> **3. The guardrails are excellent and all aimed slightly to the left of the problem.** The file-size gate doesn't check `.tsx`. The function-size gate only scans `apps/api` minus `routes/`. The boundary checker only scans `features/`. The RLS matrix only asserts cross-tenant reads on one table. Every one of these is a two-line fix to a script that already exists.

The single most important finding in this report is **not a bug in the code**. It is that **the verification layer reports success it has not earned** — the deploy pipeline ships regardless of tests, and the RLS matrix passes with tenant isolation deliberately broken. Fix those two first; everything else becomes safer to change.

## 3. Critical & high findings — security and data

### 3.1 — P0 · Production deploys are not gated on tests
`.github/workflows/{migrate,driver-ota,driver-android}.yml` vs `ci.yml`

All four workflows trigger independently on `push: main`. `grep -n "needs:\|workflow_run:"` across all five workflow files returns **zero hits**.

**Consequence:** a push to `main` that breaks every test in the repo still (a) runs `supabase db push` against the production database and (b) publishes an OTA JavaScript bundle to every driver's phone. Neither deploy job runs any test of its own. `deploy-verify.yml` is a post-hoc check, not a gate.

Compounding it: root `test` is `pnpm -r test && pnpm test:rls`, so a single unrelated unit failure means the four behavioural matrices **never execute** that run, and nothing records that they were skipped.

**Fix:** put the three deploy workflows behind `workflow_run: {workflows: [CI], types: [completed]}` with a `conclusion == 'success'` guard, or fold them into `ci.yml` as `needs:` jobs. Change the test script so the matrices always run and always report. Enable required status checks on `main`. **This is the cheapest, highest-leverage change in the entire report.**

### 3.2 — P0 · The RLS matrix passes with tenant isolation deliberately broken
`supabase/tests/rls.test.mjs`

**Reproduced, not inferred.** I copied `supabase/` to a scratch directory, mutated `0004_rls.sql` to make `drivers_select`, `ftxn_select` and `anomalies_select` read `using (true)` — i.e. every org's driver PII, fuel transactions and anomalies world-readable — and ran the matrix:

```
Baseline (unmodified):  RESULT: 209 passed, 0 failed
Mutated (3 policies open): RESULT: 209 passed, 0 failed
```

Identical. I then added two probe assertions to prove the mutation was live, and they failed as expected (`org A sees no org B fuel_transactions (0) → {"n":1}`).

**Why:** the only cross-tenant read assertion in the core block is on `vehicles` (`rls.test.mjs:236-243`). The `fuel_transactions` / `drivers` / `anomalies` assertions at `:573-588` test *driver-role scoping*, which is enforced by the independent restrictive policies from `0083_driver_rls_matrix.sql` — those still hold when the permissive org policy is opened wide. Across six seeded mutations, **four survived (67%)**.

Second, related gap: the matrix applies a **hand-maintained list of 52 migrations out of 158**. 28 of the 106 unapplied files contain policies; **43 of 191 `CREATE POLICY` statements (23%) are never loaded by any test**. Worse, `0078_role_department_rls.sql` — described in its own header as "the REAL enforcement behind the UI nav + API requireRole" — **drops and replaces** `vehicles_write`, a policy the matrix loads from `0004` and asserts against. *The matrix's role assertions describe a schema that no longer exists.* The list is also applied in a different order than production (lexical), so order-dependent DDL can diverge silently.

**Fix:** replace the hand-maintained array with `readdirSync('../migrations').sort()` and apply everything in lexical order — a failure to apply *is* the signal. Add a table-driven loop that enumerates every RLS table from `pg_policies` at runtime and asserts `count = 0` cross-tenant for each, failing on any table not covered. Then re-run the mutation harness and keep it as a scheduled CI job.

### 3.3 — P0 · A driver can self-clear a hazmat load and inject rows into another tenant
`supabase/migrations/0092_hazmat_core.sql:201`

```sql
create policy hazmat_loads_driver_update on hazmat_loads for update
  using (auth_role() = 'driver' and created_by = auth_user_id() and status = 'draft')
  with check (auth_role() = 'driver' and created_by = auth_user_id());
```

`USING` is correct. `WITH CHECK` — which governs the **post-update** row — drops both `org_id` and `status = 'draft'`. This is the only permissive policy in the entire 190-policy schema whose `WITH CHECK` omits `org_id`.

I tried to refute this four ways and could not: `hazmat_loads_driver_scope` is `as restrictive **for select**` only; `hazmat_loads_module_gate` checks the *caller's* org so it passes on the moved row; the only trigger on the table is `set_updated_at`; and no CHECK or composite FK ties `org_id` to `driver_id`. `0092`'s own header admits the guard lives elsewhere: *"the load state machine + cleared-load immutability are enforced in the API."* The API is not the only door — the anon key ships in the browser bundle, and `0103_hazmat_module_rls.sql:17` records a **measured** direct-PostgREST write against this very table.

**Two failure modes:**
- `PATCH .../hazmat_loads?id=eq.<own draft>` with `{"status":"cleared"}` → a DOT-regulated hazmat load is cleared with no `hazmat_reviews` row and no safety-manager involvement, bypassing the separation of duties `0092` was written to enforce.
- Same PATCH with `{"org_id":"<other org>"}` → the row lands in a victim tenant and appears to their dispatchers as a real load.

> **CORRECTION (2026-08-09, Stage 1 implementation).** I tested this against a real Postgres rather
> than reasoning from the policy text, and one half of the claim above is wrong. On the unmodified
> 0092 schema:
>
> | attempt | result |
> |---|---|
> | `status='cleared'` self-clear | **ALLOWED — the vulnerability is real** |
> | reassign `created_by` to another user | **ALLOWED — a defect not reported above** |
> | move `org_id` to another tenant | **BLOCKED** |
>
> The cross-tenant move was already refused. The reason is incidental, not designed: PostgreSQL
> applies the permissive SELECT policy to the post-update row, and `hazmat_loads_select` is
> org-scoped, so the moved row fails it. Widening that SELECT policy to `using (true)` makes the
> cross-tenant move succeed — I verified that too. So the tenant boundary here rested on the shape of
> an unrelated policy for a different command, one edit away from being real.
>
> Net: the regulatory-workflow bypass stands as reported, cross-tenant injection does not, and
> migration 0161 now makes all three explicit rather than incidental.

**Severity: HIGH** (verification downgraded this from CRITICAL — the `org_id` move is write-only pollution; the attacker cannot read the row back, so there is no cross-tenant *disclosure*). The regulatory-workflow bypass is the real damage.

**Fix:**
```sql
create policy hazmat_loads_driver_update on hazmat_loads for update
  using (org_id = auth_org_id() and auth_role() = 'driver'
         and created_by = auth_user_id() and status = 'draft')
  with check (org_id = auth_org_id() and auth_role() = 'driver'
              and created_by = auth_user_id() and status = 'draft');
```
Add a `BEFORE UPDATE` trigger refusing `org_id` changes on every tenant table, and add UPDATE cases to `hazmat_rls.test.mjs` (it currently tests SELECT and INSERT only).

### 3.4 — P1 · **VERIFY on the live DB** — RLS-bypassing RPCs may be publicly callable
Migrations `0088`, `0089`, `0096`, `0154`

The repo has a strong, consistent convention: 17 functions across 12 migrations explicitly `revoke all ... from public, anon, authenticated` then `grant execute ... to service_role`. Fourteen-plus `SECURITY DEFINER` functions skip it entirely — `emit_notification`, `revoke_push_tokens`, `notification_allowed`, `org_module_enabled`, `thread_unread_count`, `transition_anomaly`, `driver_start_load`, `driver_complete_stop`, `end_duty_session`, and others.

PostgreSQL grants `EXECUTE` to `PUBLIC` by default on `CREATE FUNCTION`, and `anon`/`authenticated` inherit PUBLIC grants — which is exactly why the other migrations write `from public` explicitly.

**If callable, the sharpest one is `emit_notification(p_org, p_user, …)`:** SECURITY DEFINER, no caller check, inserts straight into `notification_events` for an arbitrary org and arbitrary user with an attacker-controlled `deep_link`, and `p_severity='critical'` short-circuits quiet hours. Colleague `user_id`s are trivially obtained — `memberships_select` exposes them. `revoke_push_tokens(p_user)` is a one-call kill switch on any driver's safety notifications.

**Run this against production before triaging:**
```sql
select p.proname,
       has_function_privilege('anon',          p.oid, 'execute') as anon,
       has_function_privilege('authenticated', p.oid, 'execute') as auth
from pg_proc p join pg_namespace n on n.oid = p.pronamespace
where n.nspname = 'public' and p.prosecdef
order by 2 desc, 3 desc;
```
Anything returning `true` that isn't a policy helper (`auth_module_enabled`, `auth_in_thread`, `auth_driver_id` must keep `authenticated` execute) needs a `REVOKE` migration. Then add a matrix test asserting `has_function_privilege(...) = false` for every `SECURITY DEFINER` function not on an allowlist — the current harness grants `all on all tables` to a synthetic role and never models function grants at all, which is why it cannot see this.

### 3.5 — P1 · **VERIFY in the Supabase dashboard** — platform-admin takeover precondition
`apps/admin-api/src/lib/platformAdmins.ts:59`

`lookupPlatformAdmin` links a caller to a `platform_admins` row by matching the JWT `email` claim and then permanently writes `user_id`. **No email-verification check exists anywhere** — a repo-wide grep for `email_verified` / `email_confirmed_at` returns zero hits. The seeded owner rows deliberately ship with `user_id` NULL (the deploy runbook says so explicitly), and the admin plane shares the customer plane's Supabase project.

The `aal2` gate does **not** help: TOTP enrolment is per-user self-service on the account the attacker controls.

**Exploit path (conditional):** sign up on the customer app as `developmentteam@uncdevelopment.com` or `miki@silvicominc.com` → self-enrol TOTP → `aal2` → any `/admin/*` call links the unlinked row → `platform_owner` across every tenant. The window closes permanently once the legitimate owner logs in once.

**Verification corrected the original claim:** the audit cited `supabase/config.toml` (`enable_signup = true`, `enable_confirmations = false`) as evidence. That file is **local-dev only** — `migrate.yml` runs `supabase db push`, never `supabase config push`. So this is **HIGH only if email confirmation is off on the hosted project, LOW otherwise.**

**Check now:** Supabase dashboard → Authentication → Providers → Email → "Confirm email" must be **ON**. Then fix the code regardless: require a verified-email claim in `verifyPlatformToken`, or drop the email fallback and link `user_id` out-of-band.

Related, same root cause: `apps/api/src/routes/invites.ts:307` authorises invite acceptance purely on the JWT `email` claim — the invite `token` generated at line 246 is **dead code, read by nothing**. (Verification downgraded this to MEDIUM: `deliverInvite` calls `generateLink`, which creates the auth user at invite time, so an attacker cannot squat the address afterward.)

### 3.6 — P1 · The migration ledger and the production schema have provably diverged
`supabase/_deploy/` (30 files), `0155_repair_schema_drift.sql`, `apps/api/src/services/schemaCheck.ts`

`supabase/_deploy/` contains 26 hand-written `apply_00NN.sql` scripts plus `all_migrations.sql`, `reconcile_schema.sql` (305 lines) and `diagnose_missing_columns.sql`. Their own headers say how they're used: *"Run this ONCE in the Supabase SQL editor BEFORE deploying, then push + re-sync."*

Pasting DDL into the SQL editor applies schema changes **without writing a row to `supabase_migrations.schema_migrations`**. `supabase db push` then skips or double-applies based on a ledger that no longer describes the database. The evidence that this happened:

- `0154_efs_alert_pipeline.sql:41` — *"Some production environments have the notification migration recorded but not the objects."* The ledger claims `0089` ran; the four tables don't exist.
- `0155` repairs two drifts, one of them *"one production schema lacked it"*.
- `0096_messages.sql` is headed `-- FuelGuard — 0090 messages` and there is no `0090` file — a migration was **renumbered after being applied**, leaving a permanent ledger orphan.
- Three separate compensating mechanisms now exist instead of a fix: a 60-entry boot-time column probe (`schemaCheck.ts`, whose last entry probes for the exact drift `0155` repaired), `applied_schema_version()`, and `reconcile_schema.sql`. The boot warning literally instructs the operator back into the out-of-band channel.
- Consequence already shipped: `0154` recreates four `0089` tables idempotently but **drops `device_push_tokens_platform_check`**, so two environments now have structurally different tables depending on deploy history.

**Fix:** freeze and archive `_deploy/`; make `supabase db push` in CI the only apply path; run `supabase migration repair` once per environment to reconcile the ledger (including `--status reverted 0090`); add a CI job that applies all migrations to a scratch DB and diffs `pg_dump --schema-only` against production. That turns drift into a build failure instead of a boot-log warning.

### 3.7 — P1 · Secrets: clean in the repo, unprotected in process
`apps/api/.env`, `apps/web/.env`, `apps/driver/.env`

**Good news, verified:** `.env` is correctly covered by `.gitignore:10`, and `git log --all -- apps/api/.env` returns nothing — **the secrets were never committed.** There are zero hardcoded secrets anywhere in source, no `service_role` reference in any client bundle, `instrument.ts` sets `sendDefaultPii: false` with a PII scrubber, and no `console.*` prints a token.

**The gap is process, not code.** `apps/api/.env` holds a live Supabase **service-role key** (bypasses every RLS policy), plus Anthropic, Resend and HERE keys. Nothing in the repo prevents those from leaving via a packaging path — and in fact they did during this audit: the source archive I built to analyse the repo included all three `.env` files, because the archive was made from the working tree rather than from `git archive`. That archive lived only on your Mac and in this session's sandbox (I've moved it to `_to_delete/` for you to remove), so this is low-exposure, not a breach. But it is a live demonstration of the failure mode.

**Fix:** (a) rotate the four keys as cheap insurance and because you now know how easily they travel; (b) add `gitleaks` or `trufflehog` to CI with push protection on; (c) build any future archive with `git archive`; (d) move the API to short-lived credentials from a secrets manager. Also: seven test private keys are committed under `apps/api/src/lib/__fixtures__/mtls/` — locally generated, so low impact, but they defeat secret-scanning signal. Generate them at test setup instead.

## 4. High findings — correctness and architecture

### 4.1 — P1 · Two detection rules produce wrong verdicts on real fleet data

Both were adversarially verified and both survived.

**(a) The reefer over-fuel rule compares a 96-hour purchase window against a 48-hour burn ceiling.**
`scoreTransaction.ts:305` builds a window **centred** on the fill — `[anchor − 48h, anchor + 48h]`, i.e. 96 hours wide. `context.ts:313` sums reefer gallons across that whole span. But `rulesBehavioral.ts:281` sizes the physical ceiling from `gph * 48 + cap`.

Concrete false positive: a paired reefer with a 50-gal tank and the default 1.5 gph burn rate, three honest 45-gal ULSR fills at T−47h, T, T+47h. Window total = 135 gal; `maxPlausible = 1.5×48 + 50 = 122`. **Fires `reefer_overfuel_rate` at weight 75, severity `high`** — and the alert text reads *"Reefer bought 135 gal in 48h"* when the purchases actually span four days, during which the reefer could legitimately burn 191 gal. This is a theft accusation against an honest driver, with wrong evidence attached.

The tractor analogue (`ruleCumulativeOverfuel`) escapes this because it derives its ceiling from `windowMiles` over the *same* span. The reefer rule is the only one hard-coding the hour count.

**Fix:** either clip the sum to `[anchor − windowMs, anchor]` (matching the trailing "rolling window" the type docs describe, and matching `cardContext.ts` which already does it that way), or pass the true window width into the rule. The same value must drive the sum, the ceiling, and the message.

*Related, same root:* because the window reaches **forward**, re-scoring is not idempotent — a fill that was clear on import can flip to `alert` purely because a later purchase entered its window. `case_level` is a function of *when* scoring ran.

**(b) `odometer_implausible_jump` cannot fire on telematics-recovered EFS fills.**
`rulesOdometer.ts:81` computes elapsed hours from `fueledAt` — the business timestamp, which for EFS date-only rows is a **noon-UTC sentinel**. But the gate in `rules.ts:66` that *selects* this rule does so based on `eventTime()` reliability, and the two sibling rules (`rapid_repeat_fueling`, `impossible_travel`) both correctly use `eventTime()`. Critically the gate is a ternary — `odometer_daily_cap` is **not** also registered, so there is no fallback.

Concrete miss: two EFS date-only fills on the same business date, both telematics-matched (recovered times 06:00Z and 09:00Z), odometer 100,000 → 101,200. True implied speed 400 mph against a threshold of 85. The rule computes `hoursBetween(12:00Z, 12:00Z) = 0`, hits the `hours <= 0` early return, and goes silent. **1,200 miles of odometer padding passes completely unchecked.**

### 4.4 — P1 · 274 of 382 Supabase calls discard `error`; nothing is ever reported
`apps/api/src` repo-wide; representative `scoring/loaders.ts:299`

```ts
const { data } = await q.order(...).range(offset, offset + PAGE - 1);
const batch = ((data ?? []) as { id: string }[]).map((x) => x.id);
ids.push(...batch);
if (batch.length < PAGE) break;
```

supabase-js returns `{ error }`; it does not throw. A PostgREST error on page 3 yields `data: null` → `batch = []` → **the loop breaks cleanly** and the caller receives a partial id list that looks complete. The scoring run reports success over a fraction of the fleet.

| idiom | apps/api | apps/web |
|---|---|---|
| `const { data } = await …` (error discarded) | **274** | 17 |
| `const { data, error } = await …` | 108 | 53 |
| `catch { console.error(…) }` and continue | 75 | — |
| silent `catch {}` | 9 | 6 |
| **`Sentry.captureException`** | **0** | **0** |

There is also **no correlation id anywhere** — no request-id middleware, no `X-Request-Id`, no trace id. ~180 `console.*` lines carry a subsystem tag but no request, org or user identifier. ### 4.5 — P1 · Driver app: offline work can be silently, permanently destroyed

Two defects in the offline engine, which is otherwise well-designed (the pure `policy.ts` layer is genuinely good — and is one of the two files whose tests never run, §5.2).

**(a) Dead-lettered work is unrecoverable, and the UI points at a screen that doesn't exist.** A driver completes a stop in a dock; dispatch has since pulled the load, so the sync returns 409; `isTransient(409)` is false, so the record goes `dead`. The badge says "1 needs attention" and the note says *"open Settings › Sync to retry."* **There is no Sync screen.** `claimNext()` selects `where status in ('pending','failed')` — a `dead` record can never be claimed, so the only available button is a permanent no-op. `retryRecord()` and `loadOutboxRecords()` — the only functions that *can* revive it — have **zero callers**. `pruneDone()` only deletes `done` rows, so the badge is permanent for the life of the install and the staged photos are never released.

**(b) The entire outbox is deleted on a keychain/key mismatch.** `getOrCreateKey()` mints a **new** key whenever SecureStore returns null. After an OS restore-from-backup or a keychain reset, the existing encrypted DB no longer decrypts → `NOTADB` → `open()` calls `deleteDatabaseAsync()` and recreates it. Every queued shift start, stop completion, photo record and message captured offline is destroyed. **The only signal is a `console.warn`** — invisible in a production build. The pending badge resets to 0 and the app reports "All synced".

**(c) Related:** `if (!ok) break;` in the drain loop means one repeatedly-failing record at the queue head blocks everything behind it for ~20 minutes before it dead-letters and steps aside.

**Fix:** build the Settings › Sync screen the copy already promises (list `loadOutboxRecords()` filtered to `dead`, per-record Retry + Discard); on corruption, **rename** the DB file rather than deleting it, persist a flag, and show a blocking banner; continue past transient failures rather than breaking.

`services/anomalyFlagReconcile.test.ts:11` (pattern repeated in 10 files)

## 7. Frontend

The web app is above average — `DataTable.vue` is a genuine primitive with built-in loading/error/empty covering 32 of ~40 list surfaces, **zero key-less `v-for` across 139 directives in all three apps**, no reactive-destructuring or prop-mutation bugs, `SlideOver` is HeadlessUI-backed everywhere (focus trap and Esc for free), and the design-token linter passes clean. **P2 — 13 of 25 raw form controls have neither a bound `id` nor an `aria-label`**, including `SearchInput` (the search box on all 21 filtered pages — placeholder only, which disappears on typing) and the resolution-note textarea required to resolve or dismiss an alert. `FormField.vue` does this correctly with `useId()`; it just isn't used there. **P3 — no virtualised lists in the driver app.** `FlatList` appears **zero** times; every list is `.map()` inside a `ScrollView`. A months-long dispatch thread mounts every message at once with no recycling, on a min-spec Android target.

## 9. Three habits that would have prevented most of this

1. **Never accept a completion claim without an artifact.** Every false statement in §6 was written by an assistant summarising its own work. The fix is mechanical: a claim about test counts must come from `$GITHUB_STEP_SUMMARY`, a claim about migrations from `readdirSync`, a claim about a control from a test that fails when the control is removed. Prose is not evidence.

2. **When you fix something, grep for its twin.** Every §4.6 divergence started as a correct fix applied to one of two copies. Before merging a hardening change, search for the same function name, the same constant, the same pattern elsewhere — and either back-port it or delete the copy.

3. **Point the guardrails at the whole repo, not the part you were looking at.** Every fitness function here was written correctly, scoped to the directory that was open at the time, and never widened. When you add a check, add it repo-wide on day one and grandfather the violations explicitly — a waiver list you can see beats an exclusion glob you forget.
