## NEXT: SP4 — the Audit log through the API (two PRs)

### Why
`/settings/audit` (`apps/web/src/pages/AuditPage.vue`, surface `admin.settings.audit`, gate
`section("settings")`, `startsOnFor: []`) reads `audit_logs` STRAIGHT through PostgREST
(`apps/web/src/features/audit/useAudit.ts`). RLS decides who gets rows:

`audit_select`: `org_id = auth_org_id() and auth_role() in ('admin','auditor')`. This is 0004, and
production matched it on 2026-09-30.

So when the admin grants the Audit log to a fleet manager on the Permissions page, the page opens and
shows **an empty table**. A ROLE test is overriding the grant, which is the same bug SP2 fixed for saves.
(Note that `auditor` is a role that holds `settings: view`, per `packages/shared/src/auth.ts`.)

### Facts measured 2026-09-30 (production, read-only)
- `audit_logs` holds **5,064,901 rows, 1,231 MB**. 5,064,659 of them belong to ONE org, and the other
  org has 242. It is one of the three tables that make up 94% of the database
  (`database-growth-is-three-tables.md`), and the DB is Micro and swapping
  (`database-is-micro-and-swapping.md`).
- Indexes: `audit_logs_pkey (id)`, `idx_audit_org_time (org_id, created_at desc)`, and
  `idx_audit_action_trgm` (gin trigram on `action`, 0163).
- Today's query: `select id, org_id, actor_id, action, entity, entity_id, meta, created_at` with
  `count: "exact"`, ordered by `created_at desc, id desc`, `limit 51`. It takes an optional
  `ilike 'action%'` and a keyset cursor `created_at|id`.
  - ⚠ **`count: "exact"` scans the org's ~5 M rows on every page load and every filter change.**
    `AuditPage.vue` shows that total (`:count="total"`, and the pager's `:total`).
- The only client reader of `audit_logs` is `useAudit.ts`. `grep -rn 'from("audit_logs")'
  apps/web/src apps/driver` finds nothing else. Re-check this before the narrowing migration.
- There is already an `auditRouter` at `/api/audit` (`apps/api/src/modules/org/routes/audit.ts`, 155
  lines). It holds `/sample`, `/recall-metrics` and a POST, all for Recall audit and Reports, on
  `requireSection("settings", …)`. Put the log endpoint there, e.g. `GET /api/audit/log`. It is the org
  module's router, and `audit_logs` is org-owned (check `docs/ARCHITECTURE.md`'s table ownership and
  `scripts/table-writers.json`; this is a READ, so the writers manifest doesn't change).
