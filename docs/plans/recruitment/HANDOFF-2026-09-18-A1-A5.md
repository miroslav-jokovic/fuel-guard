## 2. A5a — the column, and the one thing §9 does not say

**Next-numbered migration `0345`**, adding `sign_token_hash` to `application_invitations`. Column
only — **no reader in this PR** (`lint:migration-ordering`), and A5b is the reader. Commit the
regenerated `schema.generated.sql`; ⚠ that check hides inside `lint:table-writers`.

⚠ **`token_hash` is `text NOT NULL` with a UNIQUE constraint and a unique btree index** (measured in
`schema.generated.sql`). `sign_token_hash` must be **nullable** — every existing row has none — and
the question §9 leaves open is whether it gets its own uniqueness. **Recommendation: a partial unique
index** (`where sign_token_hash is not null`). Without one, two invitations could hold the same sign
token and `resolveInvitation`'s `.maybeSingle()` would answer neither of them; with a plain UNIQUE
the NULLs are fine in Postgres but the partial index says the intent out loud and indexes only the
rows that have one.

**Verify:** `pnpm lint` (migrations + schema snapshot), and the PGlite matrix. `application-intake`,
`application-session` and `release-ceremony` are the matrices that touch this table.

**Done when:** the column exists in production and nothing reads it.

## 3. ⚠ A5b — the file is at 497 of 500, and three headers argue against the step

This is the step to read before starting, not during.

### 3a. `applicationIntake.ts` is at **497 of 500**

A5b's whole server-side change is in `resolveInvitation`, which lives there. **Three lines of
headroom.** Split first, in its own behaviour-preserving PR, exactly as #883 did for `ApplyPage.vue`
and #888 for `usePacketCeremony.ts` — a waiver is how gates die, and a refactor bundled into a feature
step is a diff in which nobody can see which lines were the feature.

### 3b. Three places carry a written decision that A5b reverses in part

⚠ **The code currently argues, at length, against putting a link in the approval email.** If A5b lands
without touching these, the repository will hold comments contradicting its own behaviour — which is
worse than no comment, because the next reader believes them:

| Where | What it says |
|---|---|
| `applicationApprovalNotice.ts` header | *"⚠ WHY NOTHING HERE ROTATES A TOKEN … the abandonment sweep's answer is to rotate the hash and email the new token (0232), and that answer is REJECTED here"* |
| `packages/shared/src/email.ts`, `renderApplicationApprovedEmail` (D-AX14) | *"⚠ IT CARRIES NO LINK, AND THAT IS THE DECISION RATHER THAN AN OMISSION"* — and it names the earlier email's subject line instead, **pinned by a test** that the two templates keep saying the same words |
| `apps/web/src/features/apply/strings.flow.ts`, `waitingNote` | the promise itself: *"keep this link, it is where you will sign, and it still works"* |

**§9's clause is right, and it is worth stating precisely why.** The objection had two halves:
*(a) there is no link to send* — A5a's column is exactly that, minted fresh; and *(b) rotating breaks
the promise* — **A5b does not rotate.** The old hash keeps working, so `waitingNote` stays true and
nobody is stranded. So the decision is **amended, not reversed**: the approval email gains a link
*and* the old one still opens. Say that in the headers, and give it a decision id rather than leaving
three files disagreeing with a fourth.

### 3c. What `resolveInvitation` has to become, and what must not change

```ts
.eq("token_hash", hash)          // today
.maybeSingle()
…
if (!row || !hashEquals(row.token_hash, hash)) return dead;
```

Accepting either hash means an `.or("token_hash.eq.…,sign_token_hash.eq.…")`, and then the
constant-time compare against **whichever column matched** — `hashEquals` exists because `===` on
anything derived from a secret is a timing oracle, and a rewrite that drops it would be a security
regression the tests cannot see.

⚠ **The neutral refusal must stay byte-identical.** Every failure returns the same `dead`
(`invalid_link`), because telling *expired* from *no such invitation* tells an anonymous caller that a
token EXISTED — which is a fact about a person applying for a job. A second lookup path is a second
place that neutrality can be lost.

**Verify:** api tests, including a refused-send test asserting the approval still commits (a mail
provider's 429 must never roll back an approval — the module's own rule), and one that opens the
session with the OLD token after a sign token has been minted.

**Done when:** an approved applicant gets an email with a link that opens the signing screen, **and
their old link still works.**
