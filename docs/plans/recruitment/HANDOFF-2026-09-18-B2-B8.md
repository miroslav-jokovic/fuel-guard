## 2. B2 — the step-one permissions PDF

**The row:** the four instruments + the e-sign consent + the certificate of completion, as one banded
interim document. ⚠ It does **not** touch D-AX8 — the filed record stays single and hashed.

### Why it stopped being optional polish

A2 moved the office's preview onto the carrier's packet, which has **no page** for the four releases,
the e-sign consent or the §391.21(b)(12) certification block. Those three facts are not lost and they
are no longer on the wrong document, which was the defect — but **they now have no printable home
until B2 builds one.** Today the only office-facing view of them is B6's `AuthorizationsPanel` behind
the Permissions row on `/recruitment/:id`, which is a screen and not something you can put in front of
somebody without a login. The reasoning is written into `preview.ts`'s header; read it first.

### What already exists, measured — most of this step is assembly

| Ingredient | Where it is | Note |
|---|---|---|
| The four instruments | `driver_authorizations` (0215/0228), served by `GET /api/recruitment/drivers/:id/authorizations` | Order is `APPLICATION_RELEASE_ORDER`; names are `AUTHORIZATION_PURPOSE_LABELS`; **the exact text and version are stored on the row** |
| The 7001(c) consent | **`esign_consents` (0227) — its own table, not a fifth authorization row** | ⚠ `driver_authorizations.esign_consent_at` is a *timestamp on each row*, not the consent. The instrument, its six clauses and its version live in 0227, written by the `record_esign_consent` RPC |
| The certificate of completion | `applicationPdf/certificate.ts` | Already a reusable function over `ApplicationPdfInput`, already has a `preview` branch that refuses to name a "Signer" nobody has been |
| The band | `applicationPdf/stamp.ts` (pdfkit) and the pdf-lib one in `packet/` | ⚠ **Two implementations, opposite y axes** — A2's note. Use the pdfkit one; this document is pdfkit's |
| Drawing helpers | `lib/pdfDraw.ts` — `field`, `heading`, `muted`, `rule` | What `certificate.ts` is built from |

**So the build is: a pdfkit document + one page per instrument from the stored text + the consent from
0227 + `certificate()` + the band.** No migration, no new storage, nothing hashed — this is rendered on
demand exactly as `preview.pdf` is.

### ⚠ Open question to settle in the PR, not silently

**Is it keyed on the driver or on the invitation?** `AuthorizationsPanel` is driver-keyed; the packet
preview is invitation-keyed; and B3 already ruled that **the live invitation is the newest un-revoked
one** and that packet marks key on *that invitation, never the driver*. A permissions PDF spanning two
invitations would be a document nobody can date. **Recommendation: invitation-keyed, beside
`/applications/:invitationId/preview.pdf` in `applicationReview.ts`**, with the driver-keyed panel
linking to the live invitation's copy — but say so in the header either way.

### Verify by rasterising

`pdftoppm -r 110 -png` and **read it**. A2's lesson is the standing one: two renderers can both
typecheck, both be tested, and produce different documents, because each test asserted its own
renderer. If B2 ends up sharing anything with `render.ts` or `packetDocument.ts`, the assertion that
matters is one payload through both paths.

## 3. B8 — ⚠ a viewer already exists, and the row does not say so

**The row:** *"Read-only, beside the data rather than a new browser tab. Shared with C1 — same viewer,
one of them read-only."*

**Measured before you start, because it changes the size of this step:**

- **`apps/web/src/components/DocumentPreview.vue` is the repo's sanctioned document viewer** (DQF plan
  B6), already promoted out of `features/` for the `lint:boundaries` reason, already used by
  `QualificationSection.vue`. It is a `BaseModal size="xl"` with an `<iframe>` for PDFs and an `<img>`
  for scans, print and download in the footer, and the thumb/normalized/original rule already reasoned
  out in its header. **Do not build a second one** — that is the D-DS18 mistake with a new name.
- **What it cannot do is the actual gap: it takes a `DocumentRow` with URLs.** A document this API
  *renders on demand* — `preview.pdf`, and B2's new one — has no row and no URL. Those go through
  `lib/documentDownload.ts`'s `openPdf`, which fetches the bytes with the session token and **opens a
  new tab**, which is the thing B8's row exists to stop. `ApplicationReviewDrawer.vue` is the caller
  to fix first.
- So **B8 is most likely "teach the sanctioned viewer to take a blob, and place it beside the record"**,
  not "build a viewer". ⚠ Verify that at the call sites before committing to either shape — a negative
  about what exists is exactly the claim this repo's own rule says to check by hand.

### ⚠ The "shared with C1" claim is a claim to TEST, not to inherit

C1 needs a **page rail, START/NEXT and tap targets over 22 named places**. An `<iframe>` gives you
none of that: you cannot address a page, you cannot draw over it, and you cannot know what the user is
looking at. That needs canvas rendering — and **`pdfjs-dist` is already a dependency and already
wired**: `apps/web/src/lib/pdfWords.ts` dynamically imports it *and solves the worker URL*, which is
the fiddly half. If B8 ships an iframe, say plainly in its header that C1 will need a canvas path, so
C1 does not open expecting to inherit one. If B8 ships the canvas path, it is a bigger step than a day
and should say so.

**Verify at 1440 and 390.** Q-HUI2 (is the signing surface usable on a phone?) is answered by
measurement in C1, and B8 is the first honest look at a PDF on a 390px screen.

## 4. The traps, all measured, all still live

| | |
|---|---|
| **Rendering finds what tests cannot — ten steps running, and B7 was the first that did not** | because it was walked at 390px and 1440px before the PR opened. ⚠ **Open the page, or rasterise the document.** Budget for it |
| **A mutation coming back GREEN usually means the TEST is at fault** | four times on 2026-09-18 alone. The cause is always a fixture too uniform to discriminate. **Write the partial case** |
| **⚠ A mutation that merely breaks the build proves nothing** | two of B7's eight first came back as 14 failures because the anchor referenced an unimported symbol. Write the mutation so it *compiles* and only the assertion can catch it |
| **A test can keep passing while the document under it is replaced** | A2's *"signs nothing"* asserted the absence of a string in an empty string. Re-read a surface's tests when you change what it renders |
| **`lint:filesize` fires on whoever touches a full file next** | `ApplyPage.vue` 496→427 (#883); `usePacketCeremony.ts` is at 481 and is Q-PKT11. Split first, in its own PR |
| **A mutation harness must not revert with a checkout** | copy the original bytes aside and copy them back. `git checkout --` is refused in a worktree-isolated session and does nothing, silently |
| **`rm` is refused by the sandbox classifier** | move files to the scratchpad instead |
| **`pnpm --filter @silvicom/web build` fails for this** | it needs the two `VITE_` vars as REAL env vars. `preview:local` handles it and takes whatever port is free (**:4179** today; four other sessions held 4173–4178) |
| **Dev-bypass API mocks are RAW JSON** | `route.fulfill` the body the endpoint returns, never `{ok,data}` — `/api/public/application` is `publicFetch`, not `apiFetch` |
| **`lint:ui-adoption` is a HARD ZERO on raw `<button>`** in pages and features |
| **`pnpm lint` is not the gate set** | `lint:boundaries`, `lint:filesize`, `lint:funcsize`, `lint:comment-claims`, `lint:table-writers`, `lint:table-access`, `lint:surfaces` all pass/fail independently, plus `--filter web lint:tokens` |
| **A plan-file conflict is NORMAL and the resolution is "keep both"** | two sessions appending dated §10 entries collide at the `## 11. Sources` boundary |
| **⚠ A conflicting PR gets NO CI at all** | `gh pr checks` reports *"no checks reported"* rather than a failure. **Check `mergeStateStatus` first** |
| **`native-android` is the slow check** | six jobs go green in ~3 minutes and the android one lands minutes later. The PR is not stuck; `mergeStateStatus` is `BLOCKED` until it finishes |

## 6. The protocol, unchanged

One step, one PR, one branch off `origin/main`. ⚠ Several chats share this working tree — check
`git branch --show-current` before every commit and push. Record progress by **appending a dated line
to §10**; never tick a row in §9. Run the gates before pushing. **Prove a test can fail** by mutating
the line it covers — and if a mutation comes back green, **suspect the test before the code.**
