**2026-11-06 · Track S · E3a: the campaign read carries each ad's image link (#2068)**

Built on 2026-11-05 by a chat that stopped; Track S adopted it on 2026-11-06 (E3), replayed onto main as E2 was.
Its merges of main carried no code of their own.

- No migration, no new route (so no Security L3 ledger lines, Q-AD38). `GET /api/ads/campaigns/:id` adds, to each
  finished image, a ten-minute signed link from the private `ad-assets` bucket, plus the asset's `language`, which
  the contract had left out. The link is never stored; the screen reads the campaign again for fresh ones.
- **Org scope:** the service role signs any path it is asked, so only paths under this org's own folder
  (`<org_id>/…`) are signed. A stored path outside it gets `url: null`. Never a public bucket URL.
- **Failure, decided at adoption:** a path storage cannot sign gets `url: null` and the others keep theirs. A
  signing call that fails outright fails the read (500), rather than showing a campaign with no pictures, where a
  person might approve an ad they have not seen (D-AD12).
- **Mutation:** 6 one-string mutants on `withImageUrls`: the folder filter, the ten minutes, the empty skip, the
  null link, the outright failure, a per-path failure. The first run left the last two standing; the two tests
  above were added for them. 6 of 6 killed.
- E3b (the Campaigns tab that shows these images) is split in two by the orchestrator's ruling: E3b-1 create +
  review, E3b-2 approve + launch + the launch gate's `not_certified` list.
