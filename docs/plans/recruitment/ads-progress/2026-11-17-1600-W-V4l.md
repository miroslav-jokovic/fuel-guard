**2026-11-17 · Track W · V4l — the publisher's video road, on FakeMeta**

Read first (2026-11-17), and it changed the design: Meta's Ad Creative Video Data reference lists `image_hash`
("Hash of an image in your image library with Facebook to use as thumbnail") beside the `image_url` the guides'
samples use. So a video ad's thumbnail is the creative's own 4:5 still, which the image road already uploads —
no public address for a private file. The Lead Ads guide's video sample puts the link inside the button's value.
The FB Video Ads guide says a system user may upload to an ad account. The pages are now headed v27.0; our client
calls v26.0 (not changed).

Built:

- `graphClient.ts` `MetaGraph.upload`: a video's bytes to the `upload_url` a start answered, with the guide's
  headers (`Authorization: OAuth`, `offset` 0, `file_size`). The token is sent only to `uploadBase` — Meta's upload
  host unless a caller set its own — and a URL on any other host or path is refused before a byte leaves.
- `simulator/fakeMetaVideos.ts`: the account's videos — start, the upload host, finish, the status read with its
  three phases, the list — and plantable fates (`error`, an error said only by an `error` object, `expired`, a
  phase spelt `completed`). `fakeMetaAds.ts` takes a `video_data` creative and refuses one naming a video still
  encoding, another account's video or an unknown thumbnail. Each refusal no page states is written as OUR reading.
- `publisherVideo.ts` `ensureVideo`, `readVideoStatus`: start → file → finish → wait for `ready`. The ledger row
  `video:<creative>:<lang>` is completed when the session opens and holds the video id; a later attempt asks Meta
  where that video stands and does only what is missing. `videofile:<creative>:<lang>` records how the upload and
  the encoding went.
- `publisherAds.ts`: a creative with `motion` gets `video_data` in place of `link_data`; `sameSpec` compares the
  video, the thumbnail, the words, the form and the link, and refuses an image creative found under a motion ad's
  name. `publishCampaign.ts` reads `ads_creatives.motion`.
- `contract/faultProxy.ts`: forwards raw bytes and the two headers to the target's upload host; a fault can let
  the first matching calls through (`skip`: a start and a finish share one path); an overlay can be limited to a
  number of reads and to reads asking for exactly `status`.
- Fixed on the way: a read-back that failed kept Meta's code behind a `readback_` prefix, so a token revoked
  between a create and its read-back never reached the connection alert.

Ours, to be settled on the sandbox (L4): the wait for `ready` before the creative (12 reads, 5 s apart — not
measured); `image_hash` accepted by a video LEAD ad; what a second finish answers; whether 1080 wide is refused
(Q-APX17, the fake does not measure).

Not built: the `video` kind in `CAMPAIGN_WORKERS`, `motion` in `PLAN_FORMATS_BUILT`, the review player.

Tests: `publisherVideo.test.ts` (fake-only), `publisherVideo.contract.test.ts` (both targets, real MP4s from the
simulator's clip), `graphUpload.test.ts`; the fake's new reading `video-session` in `readings.recorded.json`.

Mutants: 47 planted one at a time after a clean run, timeouts counted apart. 43 caught at once, none by a timeout
alone. Four survived and each named a test that proved less than it said: `video_status: "error"` with no failing
phase; a session adopted across two ads holding the same file; the fake refusing another account's video only
because that video was unfinished; the fake's upload host taking a file with any token. Each has its test now and
is caught.
