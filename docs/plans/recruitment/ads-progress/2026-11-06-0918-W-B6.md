**2026-11-06 · Track W · B6 Outcome feed — BLOCKED on Q-AD39 (#2093)** — no code, no migration. **Outcome feed stays L0.**

- **Why it stopped:** the brief said B6 should not need a migration, and to stop if it did. It does.
  `ads_outcome_events.stage` (0537) allows `contacted, qualified, applied, hired, lost`, which are the names from
  before Q-AD37. `LeadOutcomes` reports `contacted, converted, applied, hired, lost_after_conversion`. `converted`
  could only be stored as `qualified`, the name Q-AD37 ruled out. `lost_after_conversion` would lose its
  qualifier as `lost`. The table is an append-only evidence table, so a wrong name could never be corrected in
  place.
- **Also found (no migration needed; fixed inside B6 once unblocked):**
  - `LeadOutcome` has no platform lead id, though recruiting stores it as `recruiting_leads.channel` /
    `external_ref`.
  - It has no stage-row id for `event_id`. Proposed: derive the id as `<lead id>:<stage>`, and let the ledger's
    unique key do the dedup.
- **Trap for the migration PR:** `adsSchemaParity.test.ts` reads only `create table` bodies. A CHECK replaced by
  `alter table … add constraint` would be invisible to it, so the test has to learn the newer form in the same PR.

  derive `OUTCOME_STAGES` from it, (b) and (c) refused. Recommendation: (a) as its own PR, then B6.
