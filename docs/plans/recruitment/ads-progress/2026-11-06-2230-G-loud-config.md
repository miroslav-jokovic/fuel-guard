**PR 2 (this entry's PR). A deploy that cannot do "Confirm it's you" now says so.**

- **One definition:** `stepUpMissing` / `stepUpReadiness` / `stepUpBootWarning` in `envAuth.ts`. It checks SUPABASE_URL,
  SUPABASE_ANON_KEY, and SECRETS_ENCRYPTION_KEY through `canMintStepUp` (`lib/stepUpToken.ts`, the same `subkey`).
  The route refuses on it before the password grant.
- **`/api/version`** reports `stepUp`: "ready" or "missing:<names>". `ok` is false and `/ready` answers 503 while
  it is not ready. `routes/version.test.ts` holds every other health input healthy to show this.
- **Boot:** the server writes one `[step-up] ⚠` warning line at startup (`app.ts`, beside `metaWebhookBootWarning`).
- **deploy-verify:** staging fails; production gets `::warning::` and a summary line. **verify:live:** non-production
  targets fail; production only warns. Both explain why in a comment: release.yml's auto-rollback cannot fix a
  missing setting.
- **Web:** `verifyStepUp` answers "verified" | "refused" | "unavailable". On 503 with code `step_up_unavailable`, the
  prompt says "The server can't confirm passwords right now. Tell your administrator." and does not mark the field
  invalid. A proxy's 503 without that code is still treated as "refused".
- **`/api/jobs/latest`:** its kinds now come from `JOB_KIND_CATALOGUE`, so `efs_store_sync` (and `fleetpal_sync` /
  `medstop_sync`) stop answering 400. The widening from 20 kinds to all of them is gated by the catalogue's `area`.
  Fuel, telematics and EFS (exactly the old 20, plus 9 siblings) stay `requireOrg`. Every other area (ads,
  recruiting, compliance including Med-Stop, finance, documents, maintenance, platform) needs Settings manage,
  like `/failed`. The reason: the route returns the whole row, and its payload, stats and error can name a lead, a
  campaign, a drug-test sync or finance totals. We read the existing `area` field rather than adding a new
  catalogue flag. `routeLedger.ts`'s reason was updated to match.
