**2026-11-06 · Track W · Q-AD40, merge 2: the outcome feed's switch, and its L3 sweep (#PR)** — no migration. **Outcome feed L2 → L3.**

- **The switch (Q-AD40 (1)):**
  - Shared `adsSettingsSchema` gains an OPTIONAL `outcome_feed: { enabled, dataset_id }`. `dataset_id` is
    digits, and the group cannot be saved on without one. `outcomeFeedOf` reads an absent group as
    `ADS_OUTCOME_FEED_OFF`, so every version saved before today parses and reads off.
  - It is `.optional()`, not a zod default, so every `AdsSettings` the web builds still type-checks (apps/web is
    not touched).
  - `NO_FEED_TARGET` is gone. `settingsFeedTargets` (`outcomes/feedTarget.ts`) reads the settings version in force,
    and both the handler and the scheduler use it.
- **The simulator (Q-AD40 (2)):**
  - The feed runs for `meta` and `simulator` connections, each with its own platform's leads and ledger rows only.
  - The simulator's FakeMeta has a dataset, `SIMULATOR_DATASET_ID` = `990000000201`. That is the id a staging
    admin saves to walk the feed.
  - Production: the target is refused (`simulatorGate`), so nothing is queued. A target handed in anyway is
    refused by the registry (`graph:simulator_not_allowed`), so nothing is sent. Both are tested.
- **⚠ For Track S (the Ads control screen), the replace-whole-object trap:** `saveSettingsVersion` stores the WHOLE
  settings object a save hands it. A form that does not carry `outcome_feed` through saves a version without it,
  and that turns the feed OFF for that carrier with no error. The Settings › Ads control form must load the
  group and send it back on every save, whatever section was edited. The test "the replace-whole-object trap: a
  save carrying the group keeps the feed on; a save without it turns it off" pins both halves. A
  `{ enabled: true, dataset_id: null }` save is refused with "Name the Meta dataset before turning the outcome feed on".
- **L3 (`outcomeFeed.sweep.test.ts`, 66 cases):**
  - The run is killed at each of 5 ledger inserts, each of 5 ledger updates, and each of 3 Conversions API calls
    whose answer is lost after Meta applied it.
  - Each kill runs × no fault, a throttle, three 5xx, a hang, and one lead refused, then 5 more days.
  - Each case ends with one ledger row per stage, exactly one accepted event per stage at Meta (none for the
    refused lead), every row final, and one bell.
- **Found by the sweep:** a run killed between recording a refusal and ringing never rang (the next run saw a
  final row and counted 0). The bell is now derived from the ledger: the newest `refused` row is its dedupe key.
- **Mutants:** 14, all red, each restored byte for byte. Two first survived and got tests: `enabled` ignored,
  and the due-row provider filter.
- **Open questions:** none new. Q-AD40 is marked built.
