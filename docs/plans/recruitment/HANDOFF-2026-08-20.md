### The loop that now exists

Recruiter creates an applicant → sends an application link → the applicant fills in and **certifies**
their own §391.21 application → it becomes their identity, employment history and §391.51(b)(1)
record → §391.23 inquiries go out to each DOT-regulated former employer and **the attempts are the
evidence** → replies land on the attempt that asked → a queue tracks the deadline we can actually
miss → hire, and it all lands in the qualification file in one transaction.

## 4. Facts that cost time this session

Add these to the 2026-08-19 list; that one still stands.

- **A CHECK constraint PASSES on NULL.** `detail ->> 'source' in ('a','b')` is NULL when the key is
  absent, and a CHECK accepts NULL — so the constraint caught a typo'd value and waved through the
  *missing* one, which is the likelier mistake. `coalesce(..., '')` is the fix. **The behavioural
  matrix caught this; reading the SQL did not.**
- **A new PGlite matrix needs the default-privileges block** before the migration loop, or a brand
  new table has no grant for `authenticated` and every read ERRORS instead of being filtered by
  policy. Copy the four-line `grant usage … alter default privileges …` exec from
  `restricted-records.test.mjs`, and set `role` INSIDE the claims JSON.
- **`expectOrgScoped` and `organizations`.** That table is filtered by primary key, which IS the
  tenant id; pass `exempt: ["organizations"]` with a reason, as `dqAlertScheduler.test.ts` does.
- **`createSupabaseRecorder` can now script an RPC FAILURE** — return `{ error: {...} }` from the
  `rpc` fixture and it comes back as a failed call. Added because the hire path had to prove it turns
  SQLSTATE `HA010` into an answer rather than a 500.
- **`lint:ui-adoption` requires `PageHeader` on every routed page.** A session-free page (the
  applicant's form) has no workspace for one; add it to the exemption list in
  `scripts/ui-system-inventory.mjs` **with the reason**.
- **A projection can silently drop a field the contract collects.** `applicationEmployerSchema` has
  collected `address_line1` since H3; 0220's `insert … select` never carried it, so the applicant
  typed an address into a hole for a week. **When adding a field to a contract, grep the RPC that
  projects it.**
- **`pnpm verify:live` can report drift mid-flight.** Railway deploys the code and `migrate.yml`
  applies the schema, and the second finishes later. Check `gh run list --workflow=migrate.yml`
  before believing a schema mismatch.
- **Regulations change what you build, so read them.** `§391.23(e)` has directed employers to the
  **Drug & Alcohol Clearinghouse since 2023-01-06** — a letter asking a former carrier for D&A
  history asks for something the regulation now routes elsewhere. Two of this session's design
  decisions came out of Cornell LII, not out of the plan.

## 6. The next session's job: architect the whole recruiting system

**The owner's framing, verbatim:** *"From Recruiter receives call → create applicant profile → finish
all checking (PSP, MVR, Drug testing, Training system with videos, Orientations and hiring)."*

**Do research and analysis FIRST. Do not start building.** What exists today is a set of correct
pieces with no spine: an application, an inquiry record, a PSP client, a hire transaction. What does
not exist is the *process* — the thing a recruiter actually works through, from a phone call to a
driver in a truck.

### 6.1 What is missing, roughly in the order a recruiter meets it

1. **The call.** There is no lead. Today the first artifact is a `drivers` row with
   `status = 'applicant'`, which assumes somebody already decided to process them. A recruiter takes
   calls that never become applications, and needs source attribution, a callback list, and a
   disposition that is not "delete the row".
2. **Pre-qualification.** Age, endorsements, experience, accident history, where they live against
   where the freight is. Cheap questions that stop an expensive process, asked before the §391.21
   application rather than after it.
3. **MVR — §391.23(a)(1).** *Required for every hire and not built at all.* `SAMBA-RECON.md` did the
   vendor recon: OAuth2 client credentials plus an API-key header, demo and production hosts, and
   **a Postman collection rather than an OpenAPI document** — the EFS lesson again. `dqCatalogue`
   already carries `mvr_preemployment` and `annual_mvr_review`.
4. **Drug & alcohol — §382.301 pre-employment, and the whole §40 apparatus.** Collection site, chain
   of custody, MRO verification, the random pool, the C/TPA relationship. **Nothing exists.** The
   `drug_test` record kind exists; the process does not.
5. **Clearinghouse — §382.701(a).** A full pre-employment query needs the driver's consent given
   *inside the Clearinghouse*, not on our paper. It also now discharges §391.23(e). `dqCatalogue`
   has `clearinghouse_preemployment`; nothing performs it.
6. **Training with video.** `docs/plans/DRIVER-TRAINING-PLAN.md` is 1396 lines and says "planning
   complete", from 2026-07-23 — **read it before designing anything new, and note its migration
   numbers are 145 behind.** Two different things are being conflated and must not be: **ELDT
   (§380.609)**, which only a provider on FMCSA's Training Provider Registry may deliver, and
   **carrier orientation training**, which is ours to build.
7. **Orientation.** Scheduling, attendance, the handbook and policy acknowledgements, the
   **§391.31 road test** (or the §391.33 licence equivalency), and the moment somebody becomes an
   employee.
8. **The hire.** H8 exists and works. It is the *only* part of the back half that does.

### 6.2 The architectural question to answer first

**Is this a pipeline, a checklist, or a state machine?** The existing surfaces have each answered
differently and they now disagree:

- `applicantPipeline.ts` derives a stage from the rows and stores nothing (H6, and it was right to).
- `dqCatalogue`/`dqFile` is a checklist of requirements with evidence kinds.
- `employer_inquiries` is an append-only log of attempts with a derived status.

A recruiting system spanning eight steps and four vendors needs one answer, and the pull towards a
`recruiting_stage` column will be strong. **The 2026-08-19 handoff's reasoning against a stored stage
still holds** — a status set separately from the act it describes goes stale — but a process with
scheduling, external vendors and callbacks has real state that is not derivable from evidence rows,
and pretending otherwise would be its own mistake. That tension is the first thing to resolve.

### 6.3 What to research, and where

- **49 CFR §391.31 / §391.33** (road test and equivalency), **§382.301** (pre-employment testing),
  **§382.701** (Clearinghouse queries), **§380 subpart F** (ELDT and the TPR). Cornell LII, read —
  not recalled. Two of this session's design decisions came from doing exactly that.
- **SambaSafety**: the committed Postman collection, and what an MVR actually returns per state.
- **The Clearinghouse**: whether it has an API at all for employers, or whether it is a portal that
  a human queries and we file the result of.
- **Drug testing**: whether the carrier already has a C/TPA, and what they can integrate with.
- **`docs/plans/DRIVER-TRAINING-PLAN.md`** in full, plus `docs/plans/training-player-mockup.html`.
- **Ask the owner** how the current process actually runs today — who calls whom, what is on paper,
  what an orientation day looks like. **This is the highest-value research and it is not in a
  regulation.**

### 6.4 The trap to avoid

Do not design the whole thing as one delivery. The session that produced this handoff worked because
each step was small, shipped, and verified against a real regulation and a real database. A
recruiting-system architecture document should end with a **sequence of steps that each stand alone**,
each with its own done-when — not a milestone six weeks out.
