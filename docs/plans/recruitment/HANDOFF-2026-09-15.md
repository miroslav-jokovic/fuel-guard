## 1. The one thing that is time-critical, and it expires the moment somebody walks the ceremony

⚠ **A filed packet is rendered ONCE and frozen.** `file.ts:140–146` looks for an existing `documents`
row and returns it with `rendered: false`; only when there is none does it render, upload and insert
with a `sha256`. That copy is then cited by its §391.51(b)(1) record. **Whatever the packet looks
like when the first driver signs is what that driver's file looks like permanently** — no later fix
reaches it.

Production holds **0 `application_packet_marks`**, so no real packet has ever been rendered. That
window is open now and closes on the first walk.

**So: settle anything about how the packet PRINTS before Wave 2 below.** One such question is already
open and was defaulted, not decided:

### ⚠ The `N/A` density on page 16 was defaulted to "every cell", not ruled on

#798 fills **every cell** of every unused education and reference row — 20 `N/A`s in the education
grid when a driver leaves it empty, 9 in references. That is literally what the owner asked for
(*"fill there so we dont have empty lines printed"*) and it leaves nowhere to write after signing.

The lighter alternative — `N/A` in the first column only — was rendered and compared. It reads much
better and **leaves 16 empty writable cells in the education grid and 6 in references**, which
defeats the reason for filling at all. **Recommendation: keep as built.** It is a one-line change in
`packetGrid.ts` (`if (!line) break;` → `if (!line || c > 0) break;`) if the owner disagrees, and it
must be made **before** the first walk.

To see both again: render with `packetFieldFill` + `renderPacketOverlay`, then
`pdftoppm -f 16 -l 16 -r 110 -png`. Do not judge it from the code — §8 of the packet plan is a
standing record that this document is not readable from a layout rule.
