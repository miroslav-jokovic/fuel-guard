## U5 — answered, and it differs from the plan

**Q: where does roster's router mount, so `/api/notes` adds no line to `app.ts`?**
**A: nowhere that can be used. Roster has no mount file, and making one would hide the mount from the
three fitness functions that check every `/api` router.** So this PR adds **one mount line and one
import line to `app.ts`**, a file §7.3 does not give track B. The orchestrator rules on it before merge.

Measured on `origin/main` (`a82e63d`):

- Roster's routers are mounted one line each in `app.ts` (lines 223–234, four `/api/roster/drivers`
  mounts with a load-bearing order comment). Nothing else mounts them. Chat's `chatMount.ts` is not a
  mount file in the sense U5 means: it is one Router under one prefix (`/api/chat`), and app.ts
  still mounts it with a line of its own.
- `routeAuth.test.ts`, `routeGates.test.ts` and `testing/routeWalk.ts` (used by `routeGateLedger.test.ts`
  and the ads route ledger) all **discover mounts by reading `app.ts`'s source** with
  `app\.use\("(\/api…)"…Router\(\)…\)`. A mount made in any other file is invisible to all three. That
  includes the 401-for-unauthenticated check, which is the tenant-safety fitness function. Moving
  roster's mounts into a roster file would shrink app.ts and quietly take five routers out of that
  check. That is the workaround CLAUDE.md forbids.
- A single roster router mounted at `/api` and serving `/roster/drivers/*` + `/notes/*` beneath it is
  worse: its `router.use(requireAuth)` would answer 401 for every `/api` path it sees, public ones
  included.
- **M15 is stale:** `app.ts` is **484 lines** on `a82e63d`, not 499. With this PR it is 486. That is
  under the 500 budget and inside the 450 warning band it was already in.

**Options for the orchestrator:**
(a) Keep the line (recommended). It is the precedent every module follows, and the line is what lets
`routeAuth` prove `/api/notes` answers 401 unauthenticated. Its CI run proves that.
(b) Extend the three detectors to read a named list of mount files, then move roster's mounts out.
That is a change to three test files in no track, and it is worth doing only when app.ts actually
reaches its budget.

## Checked against UN1 (#2280, `0590_unit_notes.sql`)

These were written blind at first, because UN1 had no branch pushed. Then they were read against #2280 and
match it on every point. The recorder fixtures pin each one:

- `unit_notes_search(p_org, p_kinds text[], p_subjects jsonb, p_q, p_author, p_from, p_to,
  p_before_at, p_before_id, p_after_at, p_after_id, p_limit)`:
  - `p_subjects` is a jsonb **array of `{ "kind", "id" }`**; the API sends null for the wall, which 0590
    coalesces to `[]`.
  - `p_kinds` is ignored when subjects are named (the API also sends null then).
  - `p_from` is inclusive and `p_to` **exclusive**.
  - Rows come back newest first, with a `subject_label` and `mentions uuid[]`.
  - `fuzzy` is the same on every row of a page.
- `unit_note_summary(p_org, p_kinds text[])` returns one jsonb, `{}` for a kind with no notes.
- `set_unit_note_pinned(p_org, p_note, p_pinned)` returns boolean.
- Error codes, mapped:
  - **UN012** (no such unit in this carrier) and **UN013** (an applicant) → 404 `not_found`.
  - **UN015** (a mention of somebody who is not an office member) → 422 `invalid_mention`.
  - **UN020** (pin: not this carrier's note) → 404.

  UN012 and UN020 were added after reading #2280. In both cases the API's own org-scoped read answers
  first, so these mappings cover only the race between that read and the write.
- **`mentions`** come from 0590's `mentions` column for a listed note. A just-added note has no such
  column, so the body's tokens are read with chat's `chatMentionIds`: the same function 0590's
  trigger indexes, via `chat_mention_ids`. This was also adopted after reading #2280; at first every
  note read its body.
- The insert's `.select()` reads only `unit_notes`' own columns. The label comes from the subject read
  that comes before the insert, which is also the API's org-scoped 404.

## Decisions made inside the step

- Audit actions `notes.added`, `notes.pinned` and `notes.unpinned` use entity `unit_notes`, the note's id,
  and `meta: { kind, subjectId }`. The body is never in the audit, the rule `recruiting/routes/notes.ts`
  already follows. A test asserts it.
- `next` is set only when a first or older page comes back full (`UNIT_NOTE_PAGE_LIMIT`). A refresh
  (`after`) is never offered an older page.
- A page is `fuzzy` when every row on it came from the trigram pass (D-UN7 runs that pass only when
  the word pass finds nothing).

## Proved

- The driver role gets **403 with code `forbidden`** on all five routes, including `/people`, before
  any note query or RPC. An office role the screen is dark for gets **403 `surface_denied`**. An admin
  passes. Five office roles, accountant among them, read, write and pin.
- `expectOrgScoped` runs on every success path. Every RPC is checked to have been handed `p_org: ORG`.
- **Mutations**: each of these turned a test red: the org filter dropped from the subject read, the
  org filter dropped from the pin read, `p_org` nulled, the day's end made inclusive, `next` offered
  on a refresh, `fuzzy` forced false, UN015 unmapped, `mentions` emptied, the driver label read from
  the wrong table, `requireRole` removed, `requireSurface` removed, the body put in the audit, and the
  pin and unpin actions swapped. Two mutants **survived at first**, and each exposed a weak test:
  - `p_kinds` passed even when subjects were named. The test did not send `kind=` with subjects; it
    now does.
  - The org filter dropped from the driver read. That test did not assert org scope; it now does.

  Both mutants now die.

## A second file outside §7.3: `scripts/table-writers.json` (+1 entry)

`lint:table-writers` refuses a new write site that `scripts/table-writers.json` does not pin, and
it refuses a pinned site that does not exist ("stale"). Track A owns the manifest, but A **cannot** pin

entry would be stale there. The gate requires the pin to land in the PR that adds the writer, so this
PR adds that one entry. **A: do not add a `unit_notes` writer entry in UN1.** `table-modules.json`
(the owner, `roster`) stays A's. Measured: `check-table-writers`, `check-table-modules` and
`check-table-access` all pass on this branch, before UN1.
