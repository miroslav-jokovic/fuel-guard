## Differs from the plan: one route §4.3 does not list, `GET /api/notes/:id`

D-UN8 says a mention "opens the drawer on that note". The drawer's address needs three facts:
`?notes=<kind>:<subjectId>&note=<noteId>`. A notification row carries one `entity_type` and one
`entity_id` (`notificationEventSchema`). The web ignores `deep_link`, which `notify()` derives from
the category and the entity id alone. So one of the three ids has to stand for the rest:

- **Chosen: the entity is the NOTE** (`entity_type: "unit_note"`, `entity_id`: the note's id), and
  `GET /api/notes/:id` answers `{ note }` (an org-scoped `UnitNote`, with `kind`, `subjectId` and
  `subjectLabel`). The note's id is the only one of the three that never changes. A driver merge
  moves a note to the surviving driver (0592's guard, `DRIVER_REASSIGNMENTS`), and a bell that named
  the driver would then open somebody who no longer exists. Another carrier's note, or a non-id,
  answers 404. The driver role gets 403 `forbidden` before any read.
- Rejected: the entity is the UNIT (`entity_type` = the kind, `entity_id` = the subject). It needs no
  route but loses the note, and it goes stale on a merge.
- Rejected: spelling the subject into `entity_type` (`"unit_note:vehicle:<uuid>"`). That puts a second
  id in a column that holds a type.

**E (UN7) must know:** `notificationRoute` for `unit_note_mention` + `entity_type === "unit_note"`
cannot produce a URL from the row alone. It needs one `GET /api/notes/:id`, then
`formatNotesParam({ subjects: [{ kind, id: subjectId }], noteId })`. If the orchestrator prefers the
unit as the entity, the change is two lines in `noteMentions.ts` and the `/:id` route goes.

## What a ring is

- **Who:** every id in the note's `mentions`, as a set, except the author. 0592 refuses a non-office
  member (UN015), so nobody else can be in the list.
- **Title:** `"<author> mentioned you on <Truck|Driver|Trailer> <label>"`.
  **Body:** the note with `@Names`, never `<@id>`, cut at 80 characters, chat's length (Q-CHAT18 (a)).
- **Dedupe key:** `unit_note_mention:<noteId>`. `uq_notification_dedupe` is per
  (org, person, key), so a retried ring for one note is heard once, and a new note naming the same
  person rings again.
- **Never fails the note:** the ring runs after the insert and its audit. `notify()` logs and
  swallows its own failure, and the name lookup fails open to "@someone". A test makes
  `emit_notification` fail and still gets 201 with an audit row.

## The `@` list

`org_member_directory(p_org_id)` (0393), filtered to `role <> 'driver'` and not suspended. That is
exactly the set 0592's UN015 accepts, so a name picked from the list is never refused on save. Sorted
by name. A failed read is a 500, never an empty list (an empty list reads as "nobody can be named").
