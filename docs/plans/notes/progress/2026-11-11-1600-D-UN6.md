## 1. The board row has no trailer id and no second seat (blocks UN6)

D-UN12 asks for one drawer with "the truck's, the driver's (both seats of a team) and the trailer's
notes". `?notes=` needs a `kind:id` for each unit. Measured on `origin/main` `a82e63d`:

| Unit | What `dispatchBoardRowSchema` sends (`packages/shared/src/dispatchBoardContract.ts`) | Can the drawer name it? |
|---|---|---|
| Truck | `vehicleId` | Yes |
| Driver, first seat | `driver: { id, name } \| null`. This is roster's paired driver (`fleetIdentityReads.ts:148`, Q-DB6) | Yes |
| Driver, second seat | Nothing. `vehicles.co_driver_id` and `loads.co_driver_id` (0493, D-LA2) exist, but `fleetIdentityReads.ts` does not read the first and the board does not send either | **No** |
| Trailer | `current.trailerUnit`, the unit number as **text**. The API holds `plan.currentTrailerId` (`livemap/dispatchBoard.ts:195`) and uses it only for warnings | **No** |

Track D cannot close this inside `features/dispatch/**`. The fix belongs to the board's owners:
`dispatchBoardContract.ts` (shared), `modules/livemap/dispatchBoard.ts` and, for the co-driver,
`modules/roster/fleetIdentityReads.ts`.

**Q-UN5 — how the board row names the trailer and the second seat.**

- **(a) Recommended:** before UN6, a small PR adds `trailerId: string | null` and
  `coDriver: { id, name } | null` to `dispatchBoardRowSchema`. `dispatchBoard.ts` fills `trailerId`
  from `plan.currentTrailerId`, which it already holds. It fills `coDriver` from the same source as
  `driver` (roster's pairing, `vehicles.co_driver_id`, read in `fleetIdentityReads.ts`), so the
  board, the map and the drawer name the same two people. This is an API and contract change with no
  migration, so it ships in one PR. The orchestrator assigns it either to itself (as with UN0) or to
  track D with those three files added to D's row in §7.3.
  - **Unverified:** whether the co-driver should come from the roster pairing or from the load
    (`loads.co_driver_id`, McLeod's team seat). The two can differ on a slip-seat day. Roster's is
    recommended because it is where `driver` already comes from.
- **(b) Rejected:** the web resolves `trailerUnit` → id through the trailers list. That keeps a
  second copy of something the API already knows (a workaround under CLAUDE.md "No workarounds").
  It would also add a second request to a board that polls every minute.
- **(c) Rejected unless the owner rules it:** ship UN6 with the truck and the first seat only, and
  add the trailer and the team later. This falls short of D-UN12 as written.

## 2. The board page is not in `features/dispatch/` (§7.3 assumed it was)

The Dispatch Board is `apps/web/src/pages/AssignmentsPage.vue` (305 lines). It owns the URL, the
board query and the truck drawer's mount. `features/dispatch/` holds the table
(`DispatchBoardTable.vue`), the column list (`BOARD_COLUMNS` in `dispatchBoardView.ts`) and the
truck drawer. The Notes column, the summary query and the cell fit in track D's files. The
`NotesDrawer` mount does not. It belongs beside `DispatchTruckDrawer` in the page: about three
lines (import, `<NotesDrawer />`, and nothing else if `useNotesDrawer` owns `?notes=`).

**Ask:** add `pages/AssignmentsPage.vue` to track D's row in §7.3, limited to the NotesDrawer mount.
If D instead mounted the drawer inside `DispatchBoardTable.vue` to stay within its files, a drawer
would sit inside a component whose documented job is "this only draws", for an ownership reason.
That is the kind of misplacement CLAUDE.md's worked example warns about.
