## 2. LM10, and what the plan does not yet know

The step is at `docs/plans/livemap/LIVE-MAP-PLAN.md` §5 LM10. It is accurate. Three additions:

### 2a. The migration is a NEW TABLE, so its reader may ship in the same merge

`lint:migration-ordering` exempts new tables, and LM10's `user_dashboard_layout` is one. The
two-merge dance (a column and its first reader in separate merges) does **not** apply here. Do not
split this into two PRs on the mistaken belief that it does — I nearly told the owner it did.

RLS is still required (`check-rls.mjs`), and `user_surface_access` is the model to copy: same
`(org_id, user_id)` PK shape, same row-or-no-row semantics.

### 2b. D-DW3's three states are already half-built

`DashboardWidget.defaultFor` exists and is populated (`dispatch.live-map` → `["dispatcher"]`). What
LM10 adds is the **stored override**, and the three states must stay distinguishable:

- **no row** → inherit the role default;
- **empty array** → "I chose to hide everything";
- **a list** → that list, in that order.

This is the same shape `user_surface_access` already ships for the per-user surface reset, for the
same reason: an explicit "show me nothing" and "I have not chosen" must be distinguishable or a
default can never be changed for anyone who once touched the setting.

### 2c. `span` already exists and LM10 must read it

`DashboardWidget.span` is `"full" | "half"` and drives the grid. A stored layout is an ORDER, not a
geometry — the span stays in the catalogue. That is recorded in the field's own comment, which also
names it as a compromise (layout living in a permissions catalogue) rather than pretending it is not.

## 3. Two facts about the permission model that cost time this session

Both were found by fixtures behaving "wrongly" and being right.

1. **There are now TWO paths to "may this caller see money."** The widget gate resolves `accounting`
   through `canReachSurface(widget, role, modules, sections)`; `applyMoneyGate` reads
   `session.canView("accounting")`. They agree in production because both go through the same shared
   functions — but nothing checks that they agree. A test that stubs one and not the other produces a
   diff that looks exactly like a money-gate regression. **If LM10 touches either, check both.**
   Collapsing them is a reasonable follow-up and is not filed.

2. **A section override on an ADMIN does nothing, by design.** `resolveSectionAccess` returns the
   shipped access when `!isEditableRole(role)` — an admin cannot be denied. So a fixture (or a demo)
   that grants an admin `accounting: "none"` sees every dollar and looks broken. The role that really
   holds `accounting: none` is **`fleet_manager`**, and it is the one LM-F was written for.

## 4. Traps met this session, all paid for

**Browser verification:**

1. **Playwright matches the MOST RECENTLY ADDED route first.** A `**/api/**` catch-all registered
   last shadows every specific mock, and the page renders "Something went wrong" with an empty
   console. Register the catch-all FIRST.
2. **`useModulesQuery` goes straight to PostgREST**, not through `/api` — `supabase.from("org_modules")`
   — and PostgREST answers with a RAW ARRAY, no `{ok, data}` envelope. Without mocking
   `**/rest/v1/org_modules**` the whole Dispatch nav group is hidden, which looks like a missing nav
   entry and is not one.
3. **Every `vite preview` serves the one `apps/web/dist`.** Three stale servers were running on
   4173–4175 from the previous session. Rebuild between arms, or kill them.
4. `pnpm build` fails locally on missing `VITE_SUPABASE_*` while `preview:local` works — the config
   reads `process.env` directly. Not a regression, and CI is unaffected.

**Tests:**

5. **A fixture can be too EXTREME as well as too uniform.** The first interpolation assertion moved a
   truck a whole degree; the snap guard correctly fired and the test failed a correct implementation.
   The usual failure is a fixture that cannot discriminate; this is its mirror image.
6. **An equivalence harness can silently cover half a screen.** Two drafts of the `StatCard` stub were
   blind — the real card renders its label in a `<p>`, and a label-and-sub capture reads
   "Idle waste — idle hrs" whether or not the number survived the money gate. Both are recorded in
   `dashboardEquivalence.test.ts`.
7. **A snapshot run with `-u` will happily record a regression.** Where a rule can be stated, state
   it: "no currency figure anywhere on the tab for a caller without `accounting`", matched against the
   full HTML so a dollar in a hover title fails too. That is the assertion that would have caught all
   three LM-F leaks.
