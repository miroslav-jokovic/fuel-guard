## 3. What the work actually found

Four steps turned out to be materially different from their description. That is the useful part of
this handoff.

### 5.7 — the prescribed fix does not work on its own

The step says: `recordFeedSuccess` / `recordFeedFailure` stop patching `updated_at`. **That alone
changes nothing.** Migration 0091 puts a `before update` trigger on `efs_soap_credentials` running
the generic `set_updated_at()` from 0002, whose body is an unconditional `new.updated_at = now()`.
Postgres re-stamps the column on every update whatever the patch contains.

So the code-only change would have left behaviour byte-identical, the step's Verify — *"a poll does
not move `updated_at`"* — still failing, and **four new tests passing**. Caught by reading the schema
before believing the prescription. Migration 0196 carries the other half.

**The general lesson, and it is the same one as `promotionBlock`'s uncached comment:** a step's
prescribed change is a claim about the system, not a fact about it. Go and read what is actually
there.

### 5.9 — "low severity, high tidiness" was neither

Deleting 19 unreachable `env.X ?? <literal>` fallbacks turned **62 tests red at once**.

The cause is the finding: **88 fixtures across 42 files** built their environment as
`{ … } as unknown as Env`, a shape `loadEnv` can never return, because the zod schema `.default()`s
those keys. Those tests were exercising `undefined` values **no deployment can produce**. The
duplicated defaults were not protecting the product — they were propping up the fixtures.

All 88 casts are gone, replaced by `testEnv()`, which parses the schema exactly as the process does.
`Partial<Env>` immediately caught `EFS_SOAP_BACKFILL_RPS` in `efsCardUnresolved.test.ts`: a setting
that is not in the schema and had been configuring nothing.

**Three call sites already DISAGREED with their schema default**, each reading as documentation of a
value the process has never used:

| key | literal at the call site | schema default |
|---|---|---|
| `EFS_SOAP_MAX_DAYS_PER_REQUEST` | 30 | **7** |
| `EFS_SOAP_BACKFILL_MAX_PAGES` | 1 | **12** |
| `EFS_SOAP_MAX_ROWS_PER_POLL` | `Infinity` | **5 000** |

Three tests asserted the deleted fallbacks, titled around *"an Env that predates these keys"*. That
state is unreachable — defaults live in the schema, compiled in — so those tests guarded an input the
program cannot receive. The property they protected (the pager cannot spin on a non-number) is now
asserted against a real parsed env, where it lives.

### 5.11 — the sweep found four more silent losses

Beyond the promotion that wrote no audit row, all four losing their **entire** row every time they ran:

| where | what it passed |
|---|---|
| `driverAppSettings.ts` feature toggle | `result.featureKey` — a slug |
| `driverAppSettings.ts` override set | `` `${driverId}:${featureKey}` `` |
| `driverAppSettings.ts` override cleared | `` `${driverId}:${featureKey}` `` |
| `fueling/plans.ts` bulk delete | `ids.join(",")` |

**A bulk deletion of fuel plans left no trace at all.**

`writeAudit` now moves a non-uuid into `meta.entityIdRejected` and keeps the row rather than throwing.
Losing the row is the disaster; a throw would only move the loss from the audit table to the caller's
request.

### 5.6 — the fix is mount order, and both halves are protected

`requireAuth` hoisted ahead of the limiter, key on the org. `fuelCardVendorRateLimitKey` **throws**
rather than inventing a key if `req.auth` is missing, so the mount order cannot be quietly undone
into a silent return to IP keying. Reverting the hoist alone turns seven tests red, loudly.

**A prediction was wrong here and it is worth recording.** I predicted removing `keyGenerator` would
turn three tests red including the unauthenticated one. It turns exactly **two** red — the two that
describe the bucket. The third belongs to the hoist. The comment in the test file now states the
measured numbers, not the reasoned ones. **Same pattern as Step 7.7's tier prediction: right about
the shape, wrong about the mechanism.**

## 6. Environment facts this session established

- **A remote container has no live access.** No `SUPABASE_*`, no `EFS_*`, and the network policy
  refuses `*.up.railway.app`. Do not plan a session's Verify steps around live access without
  checking `curl -sS "$HTTPS_PROXY/__agentproxy/status"` first.
- **`pnpm test` needs `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY`**, not just `pnpm build`.
  Without them `apps/web` fails three suites AND `pnpm -r` aborts before `apps/api` reports at all —
  so a run that looks like "3 web failures" is actually hiding the entire API suite. Use CI's values:
  `VITE_SUPABASE_URL=https://example.supabase.co VITE_SUPABASE_ANON_KEY=ci-test-anon-key`.
- **`gitleaks` is not installed.** `pnpm lint:secrets` fails with "gitleaks is not installed", which
  is an environment gap and not a finding. Install it and run the gate properly — do not skip it:
  ```bash
  curl -sSL -o /tmp/gl.tar.gz https://github.com/gitleaks/gitleaks/releases/download/v8.28.0/gitleaks_8.28.0_linux_x64.tar.gz
  cd /tmp && tar xzf gl.tar.gz gitleaks && mkdir -p ~/.local/bin && mv gitleaks ~/.local/bin/
  export PATH="$HOME/.local/bin:$PATH"
  ```
- Everything else in `docs/32` §4 still holds: the operator CLI's shape, `echo-scan` paging itself,
  `suspend-drill --expect-org`, the 60-second batch ceiling, QA `07fe4058…` / production `86d6b3ea…`,

### G. NEW — a pre-existing test flake, found by the soak and fixed

`orchestrator.test.ts`'s apply-latency delta asserted `delayed - immediate >= RETRY_MS` and failed at
**299 >= 300** and **295 >= 300** on the untouched tree, before any Step 5 change. The two latencies
come from **separate `executeCapability` calls**, so the delta carries the difference between two
independent read durations. Given a named 25 ms tolerance; the discriminating assertion beside it
(`immediate < RETRY_MS`) is untouched, and per its own comment the delta never caught the bug anyway.

**This is why the soak was worth running even though it found no socket failures.**

### H. NEW — the unknown-vendor-element digest cannot be built yet

5.1's sixth signal. There is no *"elements the product understands"* set anywhere in the codebase to
subtract from — only `CARD_COLLECTIONS` and `VOLATILE_FIELDS`, neither of which is that. "Unknown"
would have to be invented, and **a digest full of false unknowns trains people to ignore it.** The
element inventory is a prerequisite feature, not an alert. Recorded rather than guessed.
