## 3. What the work actually found

Four steps turned out to be materially different from their description. That is the useful part of
this handoff.

### 5.7 — the prescribed fix does not work on its own

The step says: `recordFeedSuccess` / `recordFeedFailure` stop patching `updated_at`. **That alone
changes nothing.** Migration 0091 puts a `before update` trigger on `efs_soap_credentials` running
the generic `set_updated_at()` from 0002, whose body is an unconditional `new.updated_at = now()`.
Postgres re-stamps the column on every update whatever the patch contains.

So the code-only change would have left behaviour byte-identical, the step's Verify — *"a poll does
not move `updated_at`"* — still failing, and **four new tests passing**. Caught by reading the schema
before believing the prescription. Migration 0196 carries the other half.

**The general lesson, and it is the same one as `promotionBlock`'s uncached comment:** a step's
prescribed change is a claim about the system, not a fact about it. Go and read what is actually
there.

### 5.9 — "low severity, high tidiness" was neither

Deleting 19 unreachable `env.X ?? <literal>` fallbacks turned **62 tests red at once**.

The cause is the finding: **88 fixtures across 42 files** built their environment as
`{ … } as unknown as Env`, a shape `loadEnv` can never return, because the zod schema `.default()`s
those keys. Those tests were exercising `undefined` values **no deployment can produce**. The
duplicated defaults were not protecting the product — they were propping up the fixtures.

All 88 casts are gone, replaced by `testEnv()`, which parses the schema exactly as the process does.
`Partial<Env>` immediately caught `EFS_SOAP_BACKFILL_RPS` in `efsCardUnresolved.test.ts`: a setting
that is not in the schema and had been configuring nothing.

**Three call sites already DISAGREED with their schema default**, each reading as documentation of a
value the process has never used:

| key | literal at the call site | schema default |
|---|---|---|
| `EFS_SOAP_MAX_DAYS_PER_REQUEST` | 30 | **7** |
| `EFS_SOAP_BACKFILL_MAX_PAGES` | 1 | **12** |
| `EFS_SOAP_MAX_ROWS_PER_POLL` | `Infinity` | **5 000** |

Three tests asserted the deleted fallbacks, titled around *"an Env that predates these keys"*. That
state is unreachable — defaults live in the schema, compiled in — so those tests guarded an input the
program cannot receive. The property they protected (the pager cannot spin on a non-number) is now
asserted against a real parsed env, where it lives.

### 5.11 — the sweep found four more silent losses

Beyond the promotion that wrote no audit row, all four losing their **entire** row every time they ran:

| where | what it passed |
|---|---|
| `driverAppSettings.ts` feature toggle | `result.featureKey` — a slug |
| `driverAppSettings.ts` override set | `` `${driverId}:${featureKey}` `` |
| `driverAppSettings.ts` override cleared | `` `${driverId}:${featureKey}` `` |
| `fueling/plans.ts` bulk delete | `ids.join(",")` |

**A bulk deletion of fuel plans left no trace at all.**

`writeAudit` now moves a non-uuid into `meta.entityIdRejected` and keeps the row rather than throwing.
Losing the row is the disaster; a throw would only move the loss from the audit table to the caller's
request.

### 5.6 — the fix is mount order, and both halves are protected

`requireAuth` hoisted ahead of the limiter, key on the org. `fuelCardVendorRateLimitKey` **throws**
rather than inventing a key if `req.auth` is missing, so the mount order cannot be quietly undone
into a silent return to IP keying. Reverting the hoist alone turns seven tests red, loudly.

**A prediction was wrong here and it is worth recording.** I predicted removing `keyGenerator` would
turn three tests red including the unauthenticated one. It turns exactly **two** red — the two that
describe the bucket. The third belongs to the hoist. The comment in the test file now states the
measured numbers, not the reasoned ones. **Same pattern as Step 7.7's tier prediction: right about
the shape, wrong about the mechanism.**

## 4. What is OWED — none of it is optional, none of it is code

### 4.1 The two migrations apply themselves on merge — they are not a manual step

**Corrected 2026-08-16.** An earlier draft of this document told Miki to run `supabase db push` by
hand. That is not how migrations reach this project. `.github/workflows/migrate.yml` runs
`supabase db push` automatically on a push to `main` touching `supabase/migrations/**`, using the
`SUPABASE_ACCESS_TOKEN` / `SUPABASE_PROJECT_REF` / `SUPABASE_DB_PASSWORD` repository secrets, and it
is gated by `require-ci-green` so a red commit cannot migrate the database.

**So: merging this branch is what applies 0196 and 0197.** Nothing manual, and no production
database password needs to enter a session transcript in a public repository.

Attempted from this session, for the record: the Supabase CLI installed fine (2.114.0), but
`supabase link` returns `LegacyPlatformAuthRequiredError` (no access token in the container) and
`supabase db push --db-url …` returns `ECONNREFUSED` — the environment's network policy answers 403
to `CONNECT` for `nsjszqnfppczbnligxll.supabase.co` and the pooler, same as for Railway.

Both are now **proven**, not merely written — see §4.1a.

- **0196** — `efs_soap_credentials.updated_at` becomes configuration-only.
- **0197** — a card mutation may not reach a state that means the vendor was contacted (`sent`,
  `succeeded`, `drift_detected`, `partial`) without an `approved_by`. `failed` is exempt on purpose —
  see finding H, which is a near-miss worth reading before touching this file.

Both are `create or replace` + trigger swaps, both carry their rollback in the header, and neither
touches existing rows.

### 4.1a They are proven by a new matrix, not by assertion

`supabase/tests/efs-card-control-triggers.test.mjs` — **17 assertions**, auto-discovered by
`scripts/run-tests.mjs`, applying the full production ledger in PGlite and exercising both triggers.
This closed a real gap: the unit suites run against a Supabase fake and cannot reach a trigger at
all, so before this the two migrations were the only Phase 5 changes with no executable proof.

Verified by mutation, three ways:

| mutation | result |
|---|---|
| revert 0196 to 0091's unconditional `set_updated_at()` | 3 red |
| restore 0197's over-tight first draft | exactly the abandonment case red |
| remove 0197's trigger entirely | 4 red |

**And it caught a false-pass in itself first.** The first version compared `String(updated_at)`, and
`String(new Date())` renders at SECOND resolution — every write in the matrix lands inside the same
second, so every comparison said "equal". Three cases failed spuriously, and — much worse — the three
"a poll does not move `updated_at`" cases would have **passed identically against a trigger that did
nothing at all**. Fixed by comparing microsecond text from `to_char(...)` in SQL. *Ask what the
broken code would score before believing a green run.*

**Manual SQL, if you want to confirm on the real database after it migrates:**

```sql
-- A poll must NOT move updated_at.
select updated_at from efs_soap_credentials where org_id = '<qa org>';
update efs_soap_credentials set posted_last_polled_at = now() where org_id = '<qa org>';
select updated_at from efs_soap_credentials where org_id = '<qa org>';   -- unchanged

-- A configuration change MUST move it.
update efs_soap_credentials set account_id = account_id where org_id = '<qa org>';  -- no-op write
-- …still unchanged (nothing actually differed). Now a real change:
update efs_soap_credentials set enabled = enabled, endpoint_url = endpoint_url || '' where org_id = '<qa org>';
```

### G. NEW — a pre-existing test flake, found by the soak and fixed

`orchestrator.test.ts`'s apply-latency delta asserted `delayed - immediate >= RETRY_MS` and failed at
**299 >= 300** and **295 >= 300** on the untouched tree, before any Step 5 change. The two latencies
come from **separate `executeCapability` calls**, so the delta carries the difference between two
independent read durations. Given a named 25 ms tolerance; the discriminating assertion beside it
(`immediate < RETRY_MS`) is untouched, and per its own comment the delta never caught the bug anyway.

**This is why the soak was worth running even though it found no socket failures.** Final result:
**20 of 20 green** under deliberate 2× CPU load, every run logged. Against the ~1-in-4 failure rate
observed when the fault was captured, twenty clean runs is the evidence Step 5.4 asked for.

*(Runs 1–4 were at 1287 tests and 5–20 at 1289 — the two abandonment tests landed mid-soak. Both
trees carry the complete 5.4 fix and neither edit touches server teardown, so the run is valid; it is
recorded here rather than smoothed over.)*

### H. NEW — migration 0197 was nearly an outage, and the near-miss is the lesson

**Caught before commit, by asking who else writes the table.** 0197's first draft forbade *any* row
leaving `pending` without an `approved_by`. `services/efsCardUnresolved.ts` settles **abandoned**
rows — a `pending` mutation whose process died before `ledger.markSent` ever ran — straight to
`failed`. Those have no approver, because nothing got far enough to record one.

That trigger would have raised on every abandonment. And since
`uq_efs_card_mutations_one_pending` lets a stuck `pending` row block **every further mutation on that
card**, refusing the recovery sweep would have wedged the card permanently. **An audit control turned
into an outage.**

0197 now requires an approver only for the states that mean the vendor was contacted — `sent`,
`succeeded`, `drift_detected`, `partial`. `failed` is exempt, and the header says why so nobody
"tightens" it later. A real post-dispatch failure still goes through `markSent` and still carries its
approver, so the constraint keeps its meaning.

The abandonment path **had no test at all**; it has two now, one of which asserts the sweep does not
invent an approver. That test fails if someone adds one.

**The pattern: a constraint is only as safe as your list of who writes the table.** `ledger.ts` is
documented as "the only writer of `efs_card_mutations`" and it is not — the recovery sweep is a
second one, by design.

### I. NEW — the unit suites cannot reach a database trigger, and nothing said so

Both Phase 5 migrations move a rule into Postgres, and `apps/api`'s tests run against a Supabase
*fake* — so a trigger is invisible to them. Until `efs-card-control-triggers.test.mjs` existed, 0196
and 0197 were the only Phase 5 changes with no executable proof, and the earlier claim that they were
"validated" rested on the RLS matrix merely APPLYING them without error. Applying is not behaving.

**If you add a trigger, constraint or `security definer` function, it needs a matrix. The unit suites
will not tell you it is broken.**

### J. NEW — the unknown-vendor-element digest cannot be built yet

5.1's sixth signal. There is no *"elements the product understands"* set anywhere in the codebase to
subtract from — only `CARD_COLLECTIONS` and `VOLATILE_FIELDS`, neither of which is that. "Unknown"
would have to be invented, and **a digest full of false unknowns trains people to ignore it.** The
element inventory is a prerequisite feature, not an alert. Recorded rather than guessed.
