## 3. How to work — read this before writing code

### The lesson today taught, and it is the important one

**Phase 3 was verified byte-for-byte and was structurally blind to the one defect that mattered.**
Characterisation suites over the exact dispatched bytes, a cross-registry fitness test, 18/18
mutations, adversarial breakage checks on every guard — and none of it could find the override
false-negative, because **every test scripts its own after-document.** Only the vendor's real answer
could.

Offline verification proves you send what you meant to send. It cannot prove the vendor agrees. Plan
live checks as part of the step, not as a gate item to be swept up later.

### The rest, carried forward and still true

- **Run it, don't reason about it.** Every defect fixed in Phase 3 was found by running something:
  a two-step sequence returning `drift_detected`, a suite timing out at 3.1s, a fitness test
  comparing a constant to a CHECK constraint.
- **Reproduce before you fix.** Every defect has a test that failed first.
- **Verify a guard by breaking it.** Delete the line, watch the right test go red, restore. Phase 3
  did this for every guard it added; do not skip it.
- **Reusing a helper gets you all of its behaviours, not the one you wanted.**
- **Before opening a PR, re-read the diff as an adversary:** pins moved down not up; grep for
  `as any` / `@ts-ignore` / `.skip(` / `.only(` / `eslint-disable`; count deleted `expect(` against
  added; check every comment still states a property the code has.
- **`git add -A <dir>` is the wrong tool on this tree.** Miki keeps uncommitted work in
  `scripts/export-equipment-worksheet.mjs`. It was swept into a commit once this session and had to
  be rewritten out. **Stage explicit paths.** To move branches, `git stash push -- <path>` then
  `git stash apply` (apply, not pop). Never `git reset --hard` while his tree is dirty.

## 6. Open findings

### A. ⚠️ P0 — an override grant that WORKS is recorded as failed *(Step 3.11)*

**Observed live.** The badge reads `Override: 1 use left` and the toast reads *"EFS accepted the
request but the card is unchanged. Check the card in the WEX portal before retrying."*

**The badge is right.** `updateMirror` is fed from the verifying re-read, so the badge is EFS's own
answer after the write. The toast is `finalizeFailed`'s no-fault text, which fires when
`intentLanded` returns false.

**Why this is P0 and not cosmetic.** Re-granting does not overwrite — it grants again. The message
invites exactly the action the design exists to prevent: `efsCardControl.ts`'s own comment reads
*"the failure mode of a double-submitted override is a driver getting two free tanks."* The audit
row also says `card.mutation_failed` for a write that succeeded.

**Leading hypothesis, from recorded vendor data.** Both fixtures captured from this account show
`overrideAllLocations=false` — including `getCardV2.overridden.xml`, which HAS an override armed
(uses 2, location 115732). **We have never recorded this vendor returning `true`.** An all-locations
grant sends `override=N`, `overrideAllLocations=true` and possibly `locationOverride=0`; if EFS
stores or returns `false`, then `override` lands (badge correct) while one edited path differs and
`intentLanded` fails the whole mutation on it. Same shape as the H1 casing incident: a multi-field
write that mostly landed, judged wholly failed.

**The decisive read — no vendor call needed.** The ledger already stores it:

```sql
select id, status, efs_fault_code, drift, edits, created_at
from efs_card_mutations
where intent = 'override_grant'
order by created_at desc limit 5;
```

`drift->'unexplained'` names the field that did not land. **Do this before writing any fix.**

**The wrong fix, named so nobody reaches for it.** Widening `intentLanded`'s tolerance so the
mutation passes would hide every genuine partial failure on every capability — that is weakening the
guard that caught this. Defensible options, once the drift is known: a named, tested adapter for a
vendor normalisation we can prove, or a `precondition` that refuses an all-locations grant on an
account that does not honour it. Rule 4 applies — normalisation is a named, tested adapter, never an
incidental tolerance.

**Also check, while in that table:** whether ••••7550 has **two** `override_grant` rows. An operator
who saw "EFS refused" and did the reasonable thing would have granted twice — which would explain
§6.E without any sync bug at all.

### B. The override model is narrower than the vendor's *(scoping decision, before Phase 10)*

The WSDL carries **two** `override` elements:

```
override : int      in WSCardSummary, WSCardHeader   ← a use COUNT. What we implement.
override : boolean  in WSTransaction, WSTransactionV2, WSTransExtLoc, …
                                                      ← "this purchase WAS an override"
```

The card carries a counter; each transaction carries a flag. **We never read the transaction side.**
The portal's "this override is closed" view is most likely derived from it.

At least three distinct vendor mechanisms an operator would call "override":

| Mechanism | Vendor shape | Plan |
|---|---|---|
| Use-count exception | `WSCardHeader.override` + `locationOverride` + `overrideAllLocations` | **shipped** |
| Amount / product limits | `WSCardLimitv2`: `limit`, `hours`, `minHours`, `autoRollMap`, `autoRollMax`; plus refreshing limits | Phases 10, 11 |
| Quantity-bounded, route-locked | `managedFuelAction`: `qtyAllowed`, `fuelType`, `effDt`, `locationId`, `driverId`, `tripNumber` | **Phase 14.2**, design open |

Miki reports granting **50 gallons** in the portal, consumed and auto-closed on use. That is the
semantics of the third — one-shot, quantity-bounded, self-retiring. Our `<override>` int has no
amount and no expiry and cannot express it.

**What the plan already covers:** exact amount (10.1, `limits` array), multiple limit items in one
grant (`.max(10)`), and policy-sourced products (Phase 7 + 10.3).
**What it does not:** overriding non-fuel controls as *bounded exceptions* rather than permanent
edits (prompts and time restrictions are Phases 9 and 12 as permanent edits); multiple override
KINDS in one session; and `managedFuelAction` sits in the last phase with an undesigned bulk model.

**Decide this with the Phase 4.4 scanner's real output, not from the guide.** That is why 4.4 is
pulled to the front of Phase 4.

### F. `ambiguous_fuel_card_link` displayed as a refresh failure — **mechanism now proven**

`syncCards` runs roster → detail → `linkFuelCards`. The **link pass runs last and unconditionally
overwrites `sync_error`**, which both earlier passes had just set to null. A manual Refresh
(`POST /:id/refresh` → `refreshCardDetail` only) does not do this, so the message the operator sees
came from the background sweep and **the refresh itself very likely succeeded.**

One column carries two unrelated meanings and the UI reads the alarming one. It also means ••••7550
is not linked to a `fuel_cards` row, with consequences for fuel attribution.

**Fix:** a separate `link_status` column, or a structured `sync_error` of `{code, source, at}`.
Never let a linking outcome overwrite a sync outcome. **Filed into Phase 7 Step 7.5 (Mirror fixes)**,
and small enough to pull forward any time.

## 7. The pattern to keep watching

Six defects in this workstream have had the **same shape**: a check and the thing it checks are
built from **different sources of truth**, and the mismatch resolves the permissive way — or, as
today, the pessimistic way.

- **Echo guard** — expectation built from the request, so a dropped record was invisible. (2.1)
- **`editsLanded`** — compared record COUNT, so a write EFS ignored still reported landed. (2.2)
- **Element order** — the canonical diff keys by path, so it could not see order at all. (2.3)
- **Rate limiter** — an unmatched path treated as free rather than charged.
- **Optimistic locking** — a cached version compared against a live one.
- **The fraud step-up** — asked against the mirror AND against the fresh document. (3.6)
- **`intentLanded` on an override** — our expectation vs the vendor's stored value, and the
  disagreement condemns a write that worked. **(today, finding A)**

And a seventh, in a different key: **a vocabulary that moved on one side only.** `partial` was added
to the ledger's CHECK in 3.2 and written from 3.4, and `CARD_MUTATION_STATUSES` did not learn about
it until 3.8 compared the two. `mutation-check.yml`'s path filter never followed the code out of
`services/` into `efs/`. `vendorRateLimit.test.ts`'s router list had to be told twice.

**When you build or review anything called a guard, check, or assertion, ask: where does each side
come from, and what happens when they disagree?** And when code moves, grep for anything that names
its old location by hand.
