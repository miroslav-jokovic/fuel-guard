## 3. How to work — read this before writing code

You review your own work, which is structurally weak. Today produced hard evidence about what
catches bugs and what does not.

**Structural tests passed while the endpoint was broken in production twice.** `echoScan.test.ts`
proved by reading the source that the scan cannot write, uses the backfill lane, is rate-limited and
leaks no PAN. All true. All still true. And the endpoint 403'd and then 500'd on the only org it
exists for. **Neither bug was findable by reading the module; both were trivially findable by calling
it.** If you add a route, add a route-level test that calls it.

**Run it, don't reason about it.** Today: the migration was applied against a scratch Postgres before
merging; the type invariants were verified by breaking them; the echo-guard fixes were each verified
by reverting them alone. Every one of those found or confirmed something that reading did not.

**Reproduce before you fix.** Every defect fixed today has a test that failed first. The one time a
test passed on the first try (`echoScanRoute` happy path) it was passing *vacuously* on an empty
scan, and only specific assertions (`total: 1, scanned: 1`) exposed it.

**Reusing a helper gets you all of its behaviours, not the one you wanted.** #19: the scan reused
`resolveProbeCredentials` for its credential lookup and silently inherited a production gate,
answering 403 on the production org. The module had explicitly reasoned about *the other* flag.

**Before opening a PR, re-read the diff as an adversary:** pins moved down not up; grep your own diff
for `as any` / `@ts-ignore` / `.skip(` / `.only(` / `eslint-disable`; count deleted `expect(` against
added; check every comment still states a property the code has; ask what each new guard does with
malformed, null or unknown input.

## 6. Open findings — not yet fixed

### A. Override shows as still active after EFS consumed it — NEEDS LIVE DIAGNOSIS
Reported by Miki 2026-08-14. He granted an override in the EFS portal; it appeared correctly in
FuelGuard. The override was then used and disappeared on the EFS side, but FuelGuard still shows
`Override: 1 use left` on card `••••7550`, with *"Checked an hour ago"*.

**What the code says.** `override_uses` is written from `summary.override` by the ROSTER pass on
every sweep (`efsCardMirror.ts` `rosterFields`), and the detail pass writes it from
`doc.card.overrideUses`. Both set `synced_at`. So "checked an hour ago" means a pass ran an hour ago
and wrote whatever EFS reported. That points at **EFS still reporting `override=1`** rather than at a
staleness bug in our sync — but this is inference, not evidence, and it must not be treated as a
conclusion.

**The decisive test, one click:** hit **Refresh** on that card (`POST /api/fuel-cards/:id/refresh`,
a live `getCardv2`) and look again.
- Still `1 use left` → EFS itself is reporting the override as present; this is a vendor-truth
  question, not a mirror bug. Worth confirming against the WEX portal's own view and raising with
  them.
- Now clears → our sync frequency or one of the two passes is at fault; investigate
  `efsCardSyncScheduler.ts` and `EFS_CARD_SYNC_HOURS`.

Do this before writing any fix. There is no test to write until you know which it is.

### B. `ambiguous_fuel_card_link` is displayed as a refresh failure
Visible in Miki's report as *"Last refresh reported: ambiguous_fuel_card_link"*.

That string is written by `linkFuelCards` into `efs_cards.sync_error` when two `fuel_cards` rows
share a last-four and neither can be matched provably (`efsCardMirror.ts` ~line 412). It is a
**linking ambiguity, not a sync failure** — the refresh worked fine. One column is carrying two
unrelated meanings and the UI reads it as the alarming one.

Small, real, and worth fixing: either a separate `link_error` column or a UI that distinguishes them.
Card `••••7550` is a live example.

## 7. The pattern to keep watching

Five defects in this workstream have had the **same shape**: a check and the thing it checks are
built from **different sources of truth**, and the mismatch resolves the permissive way.

- **Echo guard** — expectation built from the request, so a dropped record was invisible. (2.1)
- **`editsLanded`** — compared record COUNT, so a write EFS ignored still reported landed. (2.2)
- **Element order** — the canonical diff keys by path, so it could not see order at all. (2.3)
- **Rate limiter** — an unmatched path was treated as free rather than charged.
- **Optimistic locking** — a cached version compared against a live one, recovery re-read the cache.

And a sixth, twice, in a different key: **a reader that knew about one of the two fields a prompt
can carry its value in.** Phase 1's `reportValue` bug, and again today in the mirror's
`infoValue` (#23) — `matchValue` only, so changing a REPORT_ONLY prompt left the header stale.

When you build or review anything called a guard, check, or assertion, ask: **where does each side
come from, and what happens when they disagree?**
